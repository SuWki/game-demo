# 完整体验设计方案

## 文档目的

这份文档把分散在「核心循环 / 路线 / 节点 / 战斗 / 数值 / 表现 / 验证」里的结论汇总成一份总策划稿。

它解决两个问题：

- 新接手的人能先理解这款原型想给玩家带来什么体验。
- 开发、策划、表现、QA 能围绕同一套目标和验证口径推进，不用各自从局部文档里拼图。

## 一句话定义

这是一个 `8~12` 分钟、以「手动走位 + 自动攻击 + 战斗内成长 + 轻量节点推进」为核心的短局动作构筑原型。

玩家要在一局里完成三件事：

- 学会看场、走位。
- 在升级和节点选择里把一条路线打出来。
- 在后段和首领战里把这条路线打成有记忆点的结尾。

## 产品目标

### 体验目标

- 前 `30` 秒让玩家明白自己主要在做什么。
- 前 `2` 分钟让玩家看到路线信号，而不是只看到散装强化。
- 中段让玩家感到这套打法开始稳了。
- 后段让玩家感到压力在收紧、打法在收尾、结尾在逼近。
- 结算后让玩家愿意马上重开，再试一条路线或一种收尾。

### 项目目标

- 验证三条主路线是否都能在真实整局中成立。
- 验证轻量节点推进能否撑起构筑变化，不需要复杂大地图。
- 验证战斗内成长是否足以撑起重开动机，不依赖局外系统。

### 当前不做

- 不做长线局外成长。
- 不做复杂大地图探索。
- 不做叙事驱动主线。
- 不做高操作门槛的动作连招。
- 不把原型扩成完整商业化框架。

## 目标玩家与核心爽点

### 目标玩家

- 喜欢短局、快速重开的玩家。
- 喜欢轻构筑、不想先背大量系统规则的玩家。
- 喜欢「走位带来收益」而不是纯面板叠数值的玩家。

### 核心爽点

- 战斗即时爽：打中、打死、掉落、拾取、升级是一条连续回报链。
- 构筑成长爽：路线不是一次选死，而是逐步出现苗头、搭起来、稳定下来、最终打出来。
- 收尾爽：后段和 Boss 战能把前面积累的路线打法收成一个清晰结尾。

### 设计取舍

- 自动攻击降低了输入门槛，让爽点集中在位置判断、资源追击和路线抉择上。
- 短局结构压缩了学习成本，方便快速验证体验是否成立。
- 逐步成型比开局锁流派更适合原型阶段，既保留了选择感，也容易暴露组合上的问题。

## 单局结构

### 五轮骨架

当前单局固定为五轮结构，对应运行时与节点数据：

1. `opening` 前段战斗
2. `mid` 中段战斗
3. `late` 后段战斗
4. `finalPrep` 最终整备
5. `finalBattle` 首领战

### 每轮职责

#### 第 1 轮：前段立规则

- 让玩家理解走位、自动攻击、拾取经验、升级三选一。
- 首次露出路线倾向。
- 不允许大多数样本在这里直接锁死。

第一轮的任务是教会并吸引玩家，不是决定一切。如果前段就锁死，后面节点和异常的价值会大幅下降。

#### 第 2 轮：中段检定成型

- 让玩家第一次明显感觉某条路线开始稳了。
- 用精英战和更有个性的节点测试构筑组合是否真的成立。
- 保留少量改道和并轨窗口。

中段是最适合做方向确认的位置。太早稳定会变成模板化起手，太晚稳定会让构筑感发虚。

#### 第 3 轮：后段收尾

- 把路线的主要打法推到高辨识度。
- 让生存压力、追击节奏、场面管理一起上升。
- 给异常和稀有内容最后一次改写结尾的机会。

后段必须开始像结尾正在逼近，否则 Boss 战会像突然插进来。这里既要保证路线收尾，也要保留「这局和上一局不一样」的变化感。

#### 第 4 轮：最终整备

- 用一次稳定、高价值的选择补短板，或补最后一块收尾拼图。
- 明确告诉玩家接下来就是最终战。

短局项目需要一个心理缓冲点，让玩家把前面局势理解为「准备进入决战」。没有最终整备，Boss 战容易读起来像普通节点的延长版。

#### 第 5 轮：首领战

- 收掉整局压力曲线。
- 用阶段变化和场面变化验证路线能否真的打完整局。
- 给结算页提供明确叙事句点。

Boss 战是整局的设计签名。如果收尾只靠数值变高，玩家不会记住这局是怎么赢或怎么输的。

## 核心循环

开始页 -> 进入一局 -> 节点选择 -> 战斗/整备/异常 -> 战斗中击杀与掉落 -> 拾取经验 -> 升级三选一 -> 路线推进 -> 后段收尾 -> 最终整备 -> 首领战 -> 结算 -> 重开

### 循环里的四个关键动作

- 走位：解决生存、拾取和输出角度。
- 击杀：制造即时反馈和资源来源。
- 拾取：把回报从「已经赢了一拍」继续推进成「下一拍更好打」。
- 选择：把战斗结果转化成路线方向。

这四个动作分别承载操作、爽感、资源和决策，缺一个都会让单局变平。如果升级和战斗脱节，路线就只存在于面板里；如果拾取不重要，战斗就退回纯站桩刷怪。

## 三条主路线设计

当前三条路线分别是 `暴击 / 穿透 / 穿梭`，在运行时对应 `crit / pierce / dash`。

### 路线共通原则

- 所有路线都要经历「出现苗头 -> 搭起来 -> 稳定下来 -> 收尾」四层。
- 所有路线都要在战斗里能看出来，不能只在面板里成立。
- 所有路线都要允许少量偏航，但不能被混合构筑冲散主体。

### 暴击路线

#### 体验定义

- 关键词：升温、续热、爆发、集中打出来。
- 玩家感受：火力不是单次跳高，而是越打越热，最后在短窗里突然爆开。

#### 设计方案

- 前段用暴击率、射频、命中密度让玩家先感觉「这把开始热起来了」。
- 中段用精英短窗和连续击杀把「续热」读成主动追击。
- 后段用高爆伤、过载、短时输出峰值把路线收成「压着热区打到结尾」。

暴击最怕只剩数值更大，那样和普通输出成长没本质区别。让暴击绑定续热和爆点，玩家才会主动读短窗、追节奏。

### 穿透路线

#### 体验定义

- 关键词：拆线、贯穿、清线、扩面、回响。
- 玩家感受：不是单体更强，而是能把原本堵塞的敌线拆开，再把收益往后排和全场扩散。

#### 设计方案

- 前段先给玩家看到「子弹能带穿一层」的信号。
- 中段把护卫、厚线和漏怪场景做成穿透的主舞台。
- 后段把多弹道、回响、扩面与清线效率收成「越堵越该由我来解」的打法。

穿透的核心不是面板伤害，而是场面治理能力。只有当敌人真的形成线，穿透才会被读成一种打法，而不是加了一个属性。

### 穿梭路线

#### 体验定义

- 关键词：换位、擦身、回摆、蓄能、反打。
- 玩家感受：通过移动穿过风险边缘，把危险转换成输出和生存收益。

#### 设计方案

- 前段先用移速、冷却、擦身窗口让玩家意识到「动起来有收益」。
- 中段把精英封位、侧压和回线场景做成穿梭路线的能力检定。
- 后段把脉冲、无伤窗口、回摆反打收成「我能在混乱里找到回线」的独特手感。

穿梭路线最怕做成自动位移或被动闪避，那会失去玩家主动性。让收益来自真实走位，才能形成路线辨识度和可学习空间。

## 节点设计

当前节点只保留四类：`战斗 / 整备 / 异常 / 首领`。

### 战斗节点

- 提供主要经验、主要风险和主要战场模板差异。
- 随阶段推进，从基础歼灭转向精英压制、后段生存与最终收尾。

战斗是主循环的主舞台，成长必须主要发生在这里。如果主要成长被放到节点外或面板外，战斗会失去存在感。

### 整备节点

- 提供稳定、偏高品质的三选一。
- 用于补短板、补组合、补最终收尾前的关键缺口。

原型仍需要保底修正，否则整局质量过度依赖随机性。整备节点是节奏缓冲器，能防止战斗连续高压导致体验塌陷。

### 异常节点

- 提供低频、高记忆点、带取舍的变化。
- 重点承载改道、并轨、押注、首领预读，而不是普通补给换名。

异常节点是「这一局为什么和上一局不一样」的关键记忆来源。如果异常节点只补数值，整个节点系统会退化成菜单排列。

### 首领节点

- 固定作为最终节点出现。
- 与普通战共享战斗主流程，但拥有独立模板、阶段和压力读法。

共享主流程能控制开发成本，独立模板和压力读法能保证 Boss 语义不被普通战吞没。

## 战斗设计

### 战斗的三层任务

- 让玩家感受到压力。
- 让玩家感受到成长。
- 让路线差异真正落地。

### 回报链

当前战斗必须稳定读出这条链：

打中 -> 打死 -> 掉经验 -> 主动追过去捡 -> 获得升级或下一拍追击优势

这是把动作反馈和构筑成长接起来的关键管道。只要这条链偏软，玩家就会觉得系统完整但不够上头。

### 战斗家族分工

#### 普通歼灭战

- 负责立规则和稳定推进。
- 重点验证基础走位、清线和资源追击。

#### 精英压制战

- 负责中段小高潮。
- 重点验证「先拆护卫 / 再追本体」的战斗打法是否成立。

#### 生存压制战

- 负责后段收尾。
- 重点验证构筑在持续压力下是否还能维持打法与效率。

#### 首领战

- 负责最终收尾。
- 重点验证路线在高压阶段变化下是否仍能打出来。

## 首领设计

### 设计方案

- 首领不是简单更厚，而是更像一个带阶段的场面控制者。
- 当前 Boss 应分别对应三条路线的主要打法压力：
  - 追猎首领：更强调续热与爆点兑现。
  - 锁域首领：更强调封位、换边和回线。
  - 屏卫首领：更强调拆屏、清线和贯穿收尾。

让 Boss 与路线形成对位关系，结尾才会显得这局的 build 真被考到了。如果 Boss 只是通用大怪，路线成型的意义会在终局被稀释。

## 数值与成长设计

### 成长来源

- 击杀掉经验球。
- 拾取经验球后升级。
- 升级三选一推进路线或补稳定器。
- 节点与异常提供结构化分叉。

### 数值原则

- 低品质内容主要负责方向信号和稳定器。
- 中段内容主要负责组合与稳定。
- 后段高品质内容主要负责收尾与记忆点。
- 同一来源在单局内不应重复到失去选择意义。

玩家需要先看到方向，再进入组合，再拿到收尾，不然整局会像乱数堆叠。数值曲线的职责不是一直上涨，而是配合阶段把体验推向不同状态。

## 表现与反馈设计

### 表现层职责

- 让玩家快速理解当前局势。
- 让阶段变化被看见。
- 让路线状态被感知。

### 必须被看见的信息

- 当前血量、经验、阶段、目标。
- 当前路线是还没稳定、已出倾向、开始稳定还是已经成型。
- 当前节点是什么、为什么值得选。
- 当前危险来自哪里。

### 表现原则

- HUD 为理解服务，不为装饰服务。
- 反馈优先靠命中、掉落、吸附、脉冲、音效和少量阶段提示来成立。
- 不用大量说明文字掩盖玩法问题。

原型阶段最重要的是读得懂、记得住、愿重开。过重的 UI 会掩盖真正的问题，也会增加维护成本。

## 验证与观测

### 关键验证问题

- 玩家是否在前 `30` 秒理解玩法。
- 玩家是否在前 `2` 分钟看到路线信号。
- 路线是否在中段稳定下来，而不是过早锁死或长期飘着。
- 后段和 Boss 是否让玩家感到结尾正在收紧。
- 结算是否能支撑重开动机。

### 关键观测指标

- 首次升级时间。
- 路线倾向首次出现时间。
- 路线开始稳定的时间。
- 路线成型时间。
- 是否发生转线或并轨。
- 稀有内容与异常内容命中率。
- 首领阶段命中率与最终结局摘要完整性。

这个项目最危险的问题不是能不能跑，而是是不是在自然样本里稳定地好玩。所以必须用最小但有效的观测去判断设计真假，而不是只靠试玩时的单次印象。

## 当前版本推进建议

### 当前应继续强化的方向

- 继续压实战斗回报链，让「击杀 -> 拾取 -> 下一拍追击」更自然。
- 继续观察暴击中段稳定性。
- 继续监控 `屏卫首领` 后段火线覆盖率。
- 继续用轻量表现与音频补读感，不重开新系统。

### 当前不建议开启的方向

- 不建议新开地图系统。
- 不建议大幅扩局外成长。
- 不建议为了 Boss 体验重写整套战斗结构。
- 不建议为了路线更显眼而把前段改成开局锁流派。

## 给团队的执行口径

如果后续要继续改文档、调数值或补表现，请优先回答四个问题：

1. 这次改动服务的是前段露头、中段稳定、后段打出来，还是最终收尾？
2. 这次改动增强的是战斗读感、路线组合，还是重开动机？
3. 这次改动是否会破坏「不提前锁死路线」的原则？
4. 这次改动能否用现有观测口径验证，而不是只能靠主观描述？

- [RunEngine.ts](file:///d:/codex/codex/auto-shooter-demo/src/systems/RunEngine.ts)
  负责单局真状态，是这份方案里核心循环、路线推进、战斗结算、节点推进的主承载体。
- [nodes.ts](file:///d:/codex/codex/auto-shooter-demo/src/data/nodes.ts)
  负责五轮节点分发，是这份方案里前段露头 / 中段稳定 / 后段收尾 / 最终整备 / 最终战节奏结构的直接落点。
- [upgrades.ts](file:///d:/codex/codex/auto-shooter-demo/src/data/upgrades.ts)
  负责稳定器、路线牌、桥接牌、收尾牌的分布，是这份方案里路线四层成长和不过早锁死的主要控制器。
- [battleTemplates.ts](file:///d:/codex/codex/auto-shooter-demo/src/data/battleTemplates.ts) 与 [enemyArchetypes.ts](file:///d:/codex/codex/auto-shooter-demo/src/data/enemyArchetypes.ts)
  负责战斗家族、精英/Boss 压力与敌人性格，是这份方案里战斗打法和路线落地场景的主要载体。
- [OverlayController.ts](file:///d:/codex/codex/auto-shooter-demo/src/ui/OverlayController.ts)
  负责 HUD、面板、结果页，是这份方案里信息可读性和阶段感的主要表现层。
- [MetricsTracker.ts](file:///d:/codex/codex/auto-shooter-demo/src/systems/MetricsTracker.ts)
  负责路线、节点、Boss 和结果观测，是这份方案里验证闭环是否成立的主要数据入口。

补这一层对应关系，是为了让策划文档不只是描述体验，还能直接告诉执行层应该优先改哪一类文件。以后要复盘某个问题，也能快速判断它更像是节点分发问题、战斗模板问题、升级权重问题，还是表现层问题。
