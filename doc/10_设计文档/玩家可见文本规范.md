# 玩家可见文本规范

## 目的

统一所有玩家可见文本的写法，让文案直接、易懂，优先说明玩家会看到什么、得到什么、要承担什么。

## 适用范围

- 首页
- 升级面板
- 异常节点
- HUD / route moment / battle feedback
- 结果页主屏
- 结果页详情页
- stable smoke / QA 样板页
- 任何会进入真实页面截图、录屏或回放摘要的文本

只要文本会出现在真实页面里，就按这份规范处理。不能因为它属于 QA、smoke、demo、样板链路就保留设计语言。

## 硬规则

1. 不写内部设计词、阶段词、实现词。
2. 不写“系统解释自己”的句子。
3. 不写表头味、面板说明味、后台字段味的小标题和标签。
3. 优先写三件事：
   - 这一下会发生什么
   - 这手换来的收益是什么
   - 这手代价是什么
4. 同一条链路里，anomaly / battle / result 要用同一种玩家语言。
5. 本轮改到哪里，就顺手把附近旧词一起清掉。
6. 同一条路线的 `starter` / `bridge` / `payoff` 要各说各的，不要换个地方把同一句意思再讲一遍。

## 禁用词

以下词不能直接出现在玩家可见文本里：

- 窗口
- 短窗
- 推进
- 构筑
- 承接
- 回切
- 主路线
- 兑现
- 收口
- 成型
- 主轴
- 方向件
- 核心件
- 质变件
- 收尾件
- 钉方向
- 补核心
- 打到 payoff
- transform
- core
- direction

这些词就算出现在 stable smoke、QA 页面、结果页复盘、截图摘要里，也算违规。

## 说明腔禁令

以下口吻也不要直接出现在玩家页面上：

- `当前进度`
- `这一下会`
- `选择规则`
- `当前机体`
- `当前目标`
- `升级历程`
- `过去的对照`
- 任何像表单、面板、报表表头的标签

按钮、小标题、标签、提示条、tooltip 都按同一规则处理。  
stable smoke 只是验收样板，不代表只清样板；正式流程页面也必须一起清。

## 推荐写法

不要写抽象阶段名，改写成玩家能立刻理解的结果。

| 不要写 | 改成这种说法 |
| --- | --- |
| 钉方向 | 先打顺 / 先打开路 |
| 补核心 | 火力更重 / 连打更疼 |
| 质变件 | 直接压上 / 直接打到后排 |
| 收尾件 | 补最后一下 |
| 进入兑现态 | 已经打出来了 / 伤害开始压住了 |
| 已经成型 | 已经连上了 / 已经打顺了 |
| 主轴 | 这套火力 / 这一路打法 |

## 长度控制

- 升级描述：尽量不超过 15 个字
- 事件描述：尽量不超过 30 个字
- 提示文案：尽量不超过 20 个字
- 标题：尽量不超过 8 个字

## 结果页规则

- `summary` 只下结论，不复读节点名和阶段名。
- `route recap` 只讲这把是怎么一路打到这里的。
- `build summary` 只讲最后差在哪，不复读前两段。
- 转折点复盘只写真正把局面往前推了一手的那一下。
- 不把结果页写成日志、策划注释或系统说明。

## 快读规则

- 玩家可见信息不只要像人话，还要做到一眼能扫懂。
- 同一屏里，最重要的信息必须最先被看到，不能藏在长段落里。
- 选择页先让玩家看见“这是什么”，再看“会发生什么”，最后再看代价和补充说明。
- 同一条路线在不同页面上的说法要分工清楚：异常讲转折，战斗讲当下，结果讲最后差在哪。
- 结果页主屏先给结论，再给路线复盘，统计和时间线往后退。
- 结果页详情页先给转折点和最后断点，数据块只做补充。
- 同一屏避免复读；如果一句结论已经说过，后面的块就不要换个说法再说一遍。
- QA、smoke、截图演示页也要像真实游戏，不准出现明显占位数据、空跑时长或一眼看穿的演示痕迹。

## 自检清单

- [ ] 没有禁用词
- [ ] 读起来像玩家语言，不像设计稿
- [ ] anomaly / battle / result 说法一致
- [ ] 能看懂收益
- [ ] 能看懂代价
- [ ] 没有“阶段推进”“路线层级”这类解释口吻
- [ ] stable smoke / QA 页面里的真实截图文本也过了一遍
