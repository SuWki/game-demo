# 音频接线与实现规范

## 文档目的

这份文档回答三个问题：

1. 当前项目里的声音从哪里触发
2. 后续替换正式资产时应该接到哪里
3. 如果扩新声音，应该遵守什么边界

它面向的是实现与维护，不替代总设计和资产清单。

## 当前实现结构

当前项目声音链路很清晰：

- `RunEngine`
  负责把战斗和流程里的关键事件转成 announcement / audio cue
- `GameScene`
  负责消耗 engine announcement，并真正调用 `services.audio.play(...)`
- `PilotAudio`
  负责音乐状态、程序音合成、ducking、计数和调试快照
- `MainMenuScene / ResultScene`
  负责局外流程音和状态音乐切换

## 2026-04-20 当前补充接线口径

- `GameScene.syncAudioState()` 现在除了继续切 `menu / battle / boss / result` 外，还会同步一层轻量战斗上下文到 `PilotAudio.setCombatContext(...)`：
  - `routeFocus`
  - `encounter`
  - `intensity`
- 这不是新系统，只是把现有战场状态整理成 cue profile 可消费的最小输入。
- 后续如果继续补音效或替换正式资产，优先沿这条口径接，不要绕开它重新在别处硬判定“现在是不是精英 / Boss / route 高潮”。

## 菜单

- 文件：`src/scenes/MainMenuScene.ts`
- 行为：
  - 进入开始页时 `setMusic('menu')`
  - 点开始时 `play('start')`
  - 导出时 `play('click')`

- 文件：`src/scenes/GameScene.ts`
- 行为：
  - 常规状态 `setMusic('battle')`
  - `finalBattle` 或 Boss 战 `setMusic('boss')`
  - `result` 状态 `setMusic('result')`

## 结果页

- 文件：`src/scenes/ResultScene.ts`
- 行为：
  - 进入结果页时 `setMusic('result')`
  - 页落地时 `play('result')`
  - 重开时 `play('start')`
  - 返回菜单/导出时 `play('click')`

## 当前 `AudioCue` 语义约束

| Cue | 当前含义 | 不建议混用为 |
| --- | --- | --- |
| `click` | 轻交互 | 重要流程确认 |
| `confirm` | 决策生效 / 阶段推进 | 奖励或危险 |
| `start` | 开场 / 重开 | 普通点击 |
| `upgrade` | 奖励确认 / 升级 | 仅阶段警告 |
| `anomaly` | 异常语义 | 普通节点选择 |
| `boss` | 最终战 / 大阶段入场 | 普通精英小提示 |
| `shoot` | 稳定输出节奏 | 命中确认 |
| `dash` | 穿梭行为与脉冲 | 普通位移 |
| `hit` | 打实了 | 击杀完成 |
| `hurt` | 玩家已经受创 | 近失 |
| `kill` | 普通击杀兑现 | 暴击高光 |
| `pickup` | 回收 / 吸附 | 升级确认 |
| `crit` | 强高光 / 精英收束 | 任何普通命中 |
| `enemyShot` | 来袭、火线建立 | 近身接触伤害 |
| `nearMiss` | 擦身预警 | 真正命中 |
| `relay*` | 家族接力与局势重排 | 普通命中点缀 |
| `pressure` | 压迫脉冲 / 高压状态 | 日常 UI 提醒 |

## 关键 cue 的接线口径

## `shoot`

- 位置：玩家射击逻辑
- 语义：稳定输出底拍
- 实现注意：
  - 必须高频可重复
  - 正式版仍然要短
  - 替换后要回测是否和 `hit` 混在一起

## `dash`

- 位置：dash pulse 生效时
- 语义：不仅是位移，还代表“换位后成立的一拍”
- 实现注意：
  - 不建议做成只有风切没有冲击的声音

## `hurt`

- 位置：
  - 玩家与敌人接触
  - 玩家被敌弹命中
- 语义：已经受伤
- 实现注意：
  - 必须和 `nearMiss` 绝对区分
  - 必须比 `enemyShot` 更重

## `enemyShot`

- 位置：
  - 普通远程开火
  - 精英/Boss volley
- 语义：敌人发起火线
- 实现注意：
  - 不建议所有敌弹都做成一样
  - 后续可以在同一 cue 语义下保留普通版与 volley 版

## `nearMiss`

- 位置：敌弹擦边
- 语义：玩家刚刚险过
- 实现注意：
  - 短
  - 尖
  - 带掠过感

## `pickup`

- 位置：经验球被吸附并吃到
- 语义：回报链进入回收段
- 实现注意：
  - 当前是高频但不应过刺
  - 建议后续加连续拾取叠层，但先不要新开系统

## `pressure`

- 位置：
  - 精英 pressure pulse
  - 高压感补强事件
- 语义：压力正在压上来
- 实现注意：
  - 必须和 `boss` 入场区分
  - 更适合作为低频压迫，而不是大 stinger

## `relayStandard / relaySkirmisher / relayBrute / relayRanged`

- 位置：普通敌 live pressure 同步和 handoff
- 语义：
  - 局势在重排
  - 不同家族在接力
- 实现注意：
  - 不应过响
  - 目的是让玩家读懂敌群人格，不是喧宾夺主

## 实施边界

## 允许做的事

- 用同一个 cue 替换成正式资源
- 在不改语义的前提下做多变体轮播
- 对已有 cue 做 route tint / 场景 tint
- 在 `PilotAudio` 里继续优化增益、ducking、层级
- 在 `RunEngine` 已有事件上补更稳定的接线

## 不建议做的事

- 为单个音效需求新增大规模音频状态机
- 为了音频拆出与当前玩法无关的复杂系统
- 把战斗里所有事件都各开独立 cue，导致系统失控
- 用过多说明型 UI 音弥补战场读感不足

## 新增 cue 的判断标准

只有同时满足以下条件时，才建议新增 cue，而不是复用现有 cue：

1. 该事件对玩家理解局势很重要
2. 现有 cue 复用后会产生误读
3. 该事件在实战里重复出现，值得建立稳定语义
4. 新增后不会让混音层级失控

## 当前建议可新增的 cue

- 精英裂口打开
- 精英裂口 follow-through
- Boss phase shift
- Boss fireline sweep
- 路线 committed / matured 短签名

## 当前不建议急着新增的 cue

- 每一种普通敌受击单独一套 hit cue
- 每一种节点 hover 独立一套 UI cue
- 每种伤害数值档位都拆不同声音
- 纯表现性无玩法意义的环境音层

## 音乐实现建议

当前 `PilotAudio` 已经支持：

- `menu / battle / boss / result`
- 动态 ducking
- cue 计数
- 音频快照
- cue context 下的 route tint / encounter tint / intensity tint

如果后续替换成正式音乐资源，建议仍保持：

- 同样的四状态入口
- 同样的状态切换语义
- 同样的 ducking 优先级
- 同样的战斗上下文输入入口

不要在第一轮正式化时就把状态扩成太多层，否则会偏离项目当前边界。

## 多变体轮播建议

正式资产替换阶段，建议在 `PilotAudio` 里保留“同一 cue 多个变体”的机制。建议规则：

- `shoot / hit / kill / pickup / enemyShot / nearMiss / relay*` 允许轮播
- `start / boss / result / victory / defeat` 不必高频轮播
- `hurt / pressure` 可以少量轮播，但差异不应过大

## 混音实现建议

## 相对优先级

- `hurt / nearMiss / pressure`
- `hit / kill`
- `shoot`
- `crit / dash / relay*`
- `music`

## Ducking 口径

建议继续沿当前逻辑：

- `shoot`
  轻 duck
- `hit / enemyShot / nearMiss / relayStandard / relaySkirmisher / relayRanged`
  中轻 duck
- `kill / crit / relayBrute`
  中 duck
- `hurt / pressure / boss`
  强 duck

## cue family × context 接线策略

当前项目已经把战场差异收束到 `PilotAudio.setCombatContext(...)`，所以接线时优先考虑“复用同一语义 cue，并让上下文去着色”，而不是把每个变化都硬拆成新事件。

| cue family | 主触发入口 | `routeFocus` 作用方式 | `encounter` 作用方式 | `intensity` 作用方式 | 何时才考虑新增 cue |
| --- | --- | --- | --- | --- | --- |
| `shoot` | 玩家射击逻辑 | 轻 tint，拉开 `crit / pierce / dash` 手感方向 | 普通/精英/Boss 只做很轻差异 | 高频率时主要影响亮度和压缩感 | 只有 tint 后仍听不出路线差异时 |
| `hit` | 伤害确认逻辑 | 次级影响 | 精英/Boss 语境可加重量和短停 | 高压时可更厚，但不改“命中确认”本义 | 只有普通 hit 与精英 hit 长期误读时 |
| `kill / crit` | 击杀兑现逻辑 | `crit` 高光可更热更集中 | 精英/Boss 收束可更硬 | 强度越高越强调收口 | 只有 kill 与 crit 已经听不分家时 |
| `pickup` | 拾取与回收逻辑 | 一般不直接拆路线 | encounter 影响很弱 | 连续拾取时允许抬升层次 | 只有连拾取已成明确玩法读感需求时 |
| `hurt / nearMiss / pressure` | 危险链与高压逻辑 | 一般不走路线差异 | encounter 是主要差异源 | intensity 是主要厚度源 | 不应因为风格偏好而细拆太多 cue |
| `enemyShot / relay*` | 敌方开火与家族 handoff | 路线影响弱 | 主要按普通/精英/Boss 与家族身份变化 | intensity 决定是否更像封锁或齐射 | 只有现有语义会误导玩家局势判断时 |
| `boss / result / victory / defeat` | 大流程节点 | 不吃路线差异 | 直接对应 encounter 或页面阶段 | intensity 只做很轻微调味 | 原则上不再拆更多大状态 |

## 接线验收补充口径

为避免后续实现把文档方向重新做散，当前补充三条硬边界：

1. 不绕开 `GameScene.syncAudioState()` 和 `PilotAudio.setCombatContext(...)` 另写一套“精英 / Boss / route 高潮”的硬判定。
2. 新增独立 cue 时，必须同时更新：
   - 本文件的触发表
   - `音频资产清单与制作规范.md` 的资产表
   - 对应 AI 对接文档里的口径
3. 如果一个差异已经能用同一 cue family 的变体轮播或 context tint 解决，就不要为了“文档看起来更完整”去新增 cue。

## 验证流程

## 1. 本地基础验证

至少要做：

- `npm run build`
- 一次 full-flow 浏览器跑通
- 一次音频调试快照确认

## 2. 运行时音频确认

优先看：

- `window.__pilotAudioDebug()`

重点字段：

- `contextState`
- `desiredMusicMode`
- `currentMusicMode`
- `cueCounts`
- `peakRms`

## 3. 实战验证问题清单

每次替换或补音频后，至少问这几个问题：

- 开火是不是一直清楚存在
- 命中是不是比开火更实
- 受击是不是一定比 near miss 更重
- 精英和 Boss 进场是不是一耳朵分层
- pickup 会不会因为太亮而吵
- relay 有没有抢掉真正的战斗主链

## 4. 回归项

音频修改后至少要复检：

- 菜单进入是否有声
- 首次用户交互后是否已解锁音频
- `battle -> boss -> result` 状态切换是否正确
- replay 后音频是否回到正确状态
- cue 是否会在浏览器限制下丢失
- `window.__pilotAudioDebug()` 中 `currentMusicMode`、`cueCounts` 是否能在普通战和高压样本里同时读到真实触发

## 最小测试矩阵

每一批正式资产接入后，建议至少跑完下面这张矩阵，不然很容易只在一个舒服样本里觉得“听起来不错”。

| 场景 | 必测内容 | 通过标准 |
| --- | --- | --- |
| `menu -> start -> battle` | 首次交互解锁、开始音、普通战底盘 | 不静音，不错态 |
| 普通战 + `crit` | `shoot / hit / kill` 主链，`crit` 是否更热更集中 | 能听出高光方向，但不抢主链 |
| 普通战 + `pierce` | `shoot / hit` 是否更线性、更切线 | 不要求独立 cue，但要能听出性格 |
| 普通战 + `dash` | `dash` 是否仍像换位反打，而不是普通风声 | `dash` 不能塌回成普通位移音 |
| 精英战 | `pressure` 与普通战差异、裂口窗口是否让路 | 高压更厚，但不糊主链 |
| Boss 战 | `boss` 状态、`boss_phase_shift` 或等效结构提示 | 一耳朵知道不是普通战 |
| 低血 / 连续 near miss | `hurt / nearMiss / pressure` 三分家 | 三者不可互相误读 |
| 结果页 | `result / victory / defeat / replay` | 封口成立且不压重开意愿 |

## 输出设备最小覆盖

Web 项目很容易在耳机里成立、在外放里塌掉，所以每一批至少要补两个输出环境：

- 关闭式耳机
  检查高频亮声是否太多、结构音是否过长。
- 笔记本外放或普通桌面音箱
  检查 `hit / kill / hurt / pressure` 的中低频信息是否仍然能读到。

如果一个声音只在耳机里成立，文档上不应视为“已通过”。

## 正式资产替换建议顺序

## 第一轮

- 先替换高价值 `P0` 资产
- 不扩新 cue
- 只验证“更好听且不回退”

## 第二轮

- 补齐 `P1`
- 拉开路线与敌人家族辨识
- 微调 ducking

## 第三轮

- 视情况新增少量 `P2` 结构型 cue
- 强化精英裂口与 Boss phase 记忆点

## 2026-04-24 接线补充

- `GameScene.syncAudioState()` 的 `intensity` 已把 `battle.pierceFlowSec` 纳入计算，穿透持续窗口会影响 `PilotAudio` 的 route tint 和高压染色。

  - `routeFocus`
  - `encounter`
  - `intensity`

  - `nearMiss` 比普通 hit 更突出，但不能盖过 `hurt`。

后续如果替换正式资产，仍应从 `RunEngine -> GameScene.syncAudioState() -> PilotAudio` 这条链路消费上下文，不要另写一套路线或高压判定。
