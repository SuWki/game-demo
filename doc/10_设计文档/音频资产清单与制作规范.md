# 音频资产清单与制作规范

## 文档目的

这份文档把音频设计从“方向描述”进一步细化成可以直接制作和排期的清单。

适用对象：

- 音效设计师
- 作曲与音乐设计师
- 负责接线和替换资源的开发者
- 需要和外包或协作方沟通需求的人

## 使用方式

- 优先先做 `P0`
- `P1` 在第一轮核心替换完成后补齐
- `P2` 用于提升辨识度和记忆点，不应阻塞主线

## 优先级定义

- `P0`
  核心循环和战斗读感必须依赖的声音。
- `P1`
  强烈建议补齐的声音，负责拉开路线、敌人和阶段差异。
- `P2`
  完成度、签名感和记忆点补强。

## 命名建议

正式资产建议采用统一命名前缀：

- `ui_*`
- `music_*`
- `player_*`
- `enemy_*`
- `route_*`
- `boss_*`
- `state_*`

例如：

- `player_hit_01`
- `enemy_relay_brute_02`
- `route_crit_overdrive_enter_01`
- `boss_bastion_phase_fireline_01`

## 建议目录结构

项目当前还没有正式音频资产目录。后续如果要把正式资产纳入仓库，建议新增以下结构：

- `public/audio/music`
  放运行时直接加载的音乐循环与结果短乐句。
- `public/audio/sfx/ui`
  放 `click / confirm / start / upgrade / anomaly / result`。
- `public/audio/sfx/player`
  放 `shoot / dash / hit / kill / pickup / hurt / crit` 相关资产。
- `public/audio/sfx/enemy`
  放 `enemyShot / relay* / elite* / boss*` 等敌方与结构事件。
- `public/audio/sfx/state`
  放 `pressure`、路线成型短签名、阶段结构音。
- `public/audio/_manifest`
  放版本清单、批次记录、资产映射表。

如果母版文件也要入库，不建议直接混在运行时目录里，建议单独新增 `audio_source/masters/` 或采用外部共享盘维护。

## 通用制作规格

## 文件规格

- 采样率：`48kHz`
- 位深：`24-bit`
- 母版交付：`wav`

如果只是临时验证版本，也建议先按同一规格出母版，再由运行时决定压缩格式。

## 时长总则

| 类别 | 建议时长 |
| --- | --- |
| 微交互 | `40ms ~ 120ms` |
| 即时战斗反馈 | `50ms ~ 180ms` |
| 高光反馈 | `120ms ~ 320ms` |
| 流程切换 | `250ms ~ 900ms` |
| 音乐循环 | `8~16` 小节为宜 |

## 空间总则

- 普通战绝大多数 SFX 使用短尾或极短房间感
- 精英裂口和 Boss 转段允许更明显空间感
- 不建议大量超宽立体声尾巴，否则会吃掉近场读感

## 频谱总则

- `hit / kill / hurt / pressure` 必须有明确中低频支撑
- `shoot / nearMiss / pierce` 可以更多依赖中高频瞬态
- 不要把所有战斗声音都堆在高频区

## 变体总则

- 高频主链 cue 至少 `4` 个变体
- 中频关键 cue 至少 `3` 个变体
- 流程 UI 可以 `2~3` 个变体

## 交付包要求

每个资产批次建议至少交付四样东西：

| 交付物 | 作用 | 最低要求 |
| --- | --- | --- |
| 母版文件 | 保留可回编版本 | `48kHz / 24-bit / wav` |
| 运行时预览文件 | 供快速试听与策划评审 | `ogg` 或 `mp3` 即可 |
| 资产清单行 | 供开发接线和回填文档 | 必须包含 `资产 ID / 对应 cue / 版本号 / 优先级 / 备注` |
| 批次说明 | 说明这批替换了什么、风险是什么 | 建议一段 `md` 说明即可 |

版本号建议沿 `asset_id_v01 / v02 / v03` 走，不建议直接用“终版”“新新终版”这类口头命名。

## cue family × context 变体策略

当前项目已经有 `routeFocus / encounter / intensity` 三层上下文，所以并不是所有差异都要拆成新 cue。建议按下面的规则做：

| cue family | `routeFocus` 影响 | `encounter` 影响 | `intensity` 影响 | 当前推荐做法 |
| --- | --- | --- | --- | --- |
| `shoot` | 强 | 中 | 中 | 先做同一 cue family 的轻 tint 变体，不急着拆三条路线独立 cue |
| `hit / kill` | 中 | 强 | 中 | 先保留主语义一致，再用精英/Boss 语境拉重量和收束 |
| `pickup` | 弱 | 弱 | 中 | 先用层级和连续拾取叠感处理，不要一上来拆太多素材 |
| `hurt / nearMiss / pressure` | 弱 | 强 | 强 | 重点保证危险分层和上下文厚度，优先靠 encounter/intensity 改变 |
| `enemyShot / relay*` | 弱 | 强 | 中 | 先按敌人家族与 volley/普通语境拉开，再考虑更细分资产 |
| 路线高光结构音 | 强 | 中 | 中 | 只有在现有 tint 明显不够时，才新增 committed / matured 类独立签名 |
| 音乐循环 | 弱 | 强 | 弱 | 继续维持四状态音乐，不因为路线差异拆更多大状态 |

## 交付、接线与回填职责

为了避免“资产做出来了，但谁来接、谁来验、谁来更新文档没人负责”，建议这一轮按下面分工：

| 角色 | 主要职责 | 完成标志 |
| --- | --- | --- |
| 音效设计 / 作曲 | 按资产表出母版、预览和批次说明 | 资产可试听、可区分、命名合规 |
| 开发 | 压缩、导入、映射到现有 cue、做回归 | `window.__pilotAudioDebug()` 和 full-flow 通过 |
| 策划 / 体验 owner | 判断是否真的服务核心循环和读感 | 批准进入下一批，不要求一次全做满 |
| 文档维护者 | 更新本文件、`音频接线与实现规范.md`、必要时更新 AI 对接稿 | 文档与运行时不脱节 |

建议把每一批的接入结果都回填到一份简短批次记录里，至少写清：

- 本批替换了哪些 `asset ID`
- 有没有前提优先级
- 哪些上下文差异已经由 tint 覆盖
- 哪些结构音仍然留在下一批
