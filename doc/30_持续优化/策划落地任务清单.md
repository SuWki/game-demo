# 策划落地任务清单

## 文档目的

这份文档把 [完整体验设计方案](</E:/codex/unity-learning/doc/10_设计文档/完整体验设计方案.md>) 继续往下拆成可执行任务。

它主要回答四个问题：

- 现在最该先做什么。
- 每条工作流要做到什么程度才算签收。
- 每条工作流主要落在哪些代码和数据文件上。
- 哪些事情现在不该做，避免主线被带偏。

## 当前执行原则

- 先保主循环和战斗回报链，再谈新主题内容。
- 先让路线在实战里被读到，再补更多面板描述。
- 先让 Boss 收尾稳定，再考虑 Boss 新机制。
- 先用现有骨架补量和补读感，不重开大系统。

## 当前建议的工作流顺序

1. 核心战斗回报链
2. 三路线实战读感
3. 精英与 Boss 收尾稳定性
4. 节点与异常差异感
5. 表现与结果页收束
6. 指标、复检与签收口径

## 工作流 1：核心战斗回报链

### 目标

让普通战稳定读出：

打中 -> 打死 -> 掉落 -> 拾取 -> 追击下一拍 -> 升级兑现

### 为什么先做

- 这是整个项目当前最直接的爽感来源。
- 如果这条链不成立，路线再完整也会显得“能玩，但不够上头”。

### 具体任务

- 压实击中确认、击杀确认和经验掉落的连续感。
- 压实 `pickupLead / pickupFlow / killFlow / tempoPulse` 的承接强度。
- 确认普通战四类敌人在这条节奏里不会把画面打成纯噪音。
- 确认低血危险感不会破坏追击与判断。

### 主要落点

- [RunEngine.ts](/E:/codex/unity-learning/src/systems/RunEngine.ts)
- [battleTemplates.ts](/E:/codex/unity-learning/src/data/battleTemplates.ts)
- [enemyArchetypes.ts](/E:/codex/unity-learning/src/data/enemyArchetypes.ts)
- [PilotAudio.ts](/E:/codex/unity-learning/src/systems/PilotAudio.ts)
- [OverlayController.ts](/E:/codex/unity-learning/src/ui/OverlayController.ts)

### 验收标准

- 普通战自然样本里，玩家能明显看懂“这一拍赚到了，下一拍还在继续”。
- 普通战节奏提升主要来自场内反馈，而不是额外说明文字。
- 这轮补强后，路线站稳时间和 Boss 监控项没有明显回退。

### 当前不该做

- 不开新武器系统。
- 不开连招系统。
- 不把问题改写成地图可视化问题。

## 工作流 2：三路线实战读感

### 目标

让 `暴击 / 穿透 / 穿梭` 在实战里被读成三种不同打法，而不是三组颜色不同的数值包。

### 为什么排第二

- 战斗回报链是地基，路线读感是上层结构。
- 回报链不稳时，路线差异容易被节奏噪音吞掉。

### 具体任务

- 暴击：继续验证“续热 -> 爆点 -> 追击”的短窗逻辑是否稳定。
- 穿透：继续验证“拆线 -> 贯穿 -> 扩面 -> 清账”的场面逻辑是否稳定。
- 穿梭：继续验证“换位 -> 擦身 -> 回摆 -> 反打”的位置逻辑是否稳定。
- 检查三条路线在前段露头、中段站稳、后段兑现上的时间差是否合理。

### 主要落点

- [upgrades.ts](/E:/codex/unity-learning/src/data/upgrades.ts)
- [contentSelectors.ts](/E:/codex/unity-learning/src/data/contentSelectors.ts)
- [balance.ts](/E:/codex/unity-learning/src/data/balance.ts)
- [RunEngine.ts](/E:/codex/unity-learning/src/systems/RunEngine.ts)
- [MetricsTracker.ts](/E:/codex/unity-learning/src/systems/MetricsTracker.ts)

### 验收标准

- 三路线都能在自然样本里被玩家读成不同节奏。
- 不出现“大多数样本前段直接锁死”或“中段仍长期漂浮”的两极化。
- 路线差异主要在战斗里成立，而不是只在升级面板或结果页成立。

### 当前不该做

- 不为路线辨识度去增加大量文字说明。
- 不为了更早露头把路线改成开局锁死。
- 不为了稀有感把高记忆点全部前移。

## 工作流 3：精英与 Boss 收尾稳定性

### 目标

让精英承担中段小高潮，让 Boss 承担最终收尾，而且两者都能稳定读出，不只是逻辑存在。

### 为什么排第三

- 中段高潮和最终收尾决定整局是否“记得住”。
- 但如果普通战和路线底层还没稳，先盯 Boss 往往会把主线带偏。

### 具体任务

- 继续复检精英裂口窗口是否能被玩家真实利用。
- 继续复检 `crit / pierce` 在精英窗口里的 mini-high 是否稳定可见。
- 继续监控 `屏卫首领` 的后段火线覆盖率。
- 继续保证 Boss 的阶段变化是“压力读法变化”，不是单纯更厚更吵。

### 主要落点

- [battleTemplates.ts](/E:/codex/unity-learning/src/data/battleTemplates.ts)
- [RunEngine.ts](/E:/codex/unity-learning/src/systems/RunEngine.ts)
- [MetricsTracker.ts](/E:/codex/unity-learning/src/systems/MetricsTracker.ts)
- [nodes.ts](/E:/codex/unity-learning/src/data/nodes.ts)

### 验收标准

- 精英自然样本里，玩家能读出“先拆护卫，再追本体”。
- Boss 战能读出阶段感和收尾感，而不是普通战加长版。
- Boss 监控项稳定，但不重新劫持开发主线。

### 当前不该做

- 不开 Boss 新机制专项轮。
- 不重写整套敌人 AI。
- 不为了签收方便而只做定向脚本样本。

## 工作流 4：节点与异常差异感

### 目标

让节点系统继续承担“结构变化”和“这局和上一局不一样”的职责，而不是退化成普通奖励排列。

### 为什么排第四

- 节点是放大路线与变化感的结构层。
- 但它必须建立在战斗和路线读感已经能被稳定感知的基础上。

### 具体任务

- 复核前段、中段、后段节点的职责是否仍然清晰。
- 检查整备节点是否承担了“保底修正”而不是“万能强牌”。
- 检查异常节点是否还保有改道、并轨、押注、Boss 预读语义。
- 检查节点候选是否既有路径感，又不把项目拖成复杂地图。

### 主要落点

- [nodes.ts](/E:/codex/unity-learning/src/data/nodes.ts)
- [events.ts](/E:/codex/unity-learning/src/data/events.ts)
- [anomalyRoutePools.ts](/E:/codex/unity-learning/src/data/anomalyRoutePools.ts)
- [RunEngine.ts](/E:/codex/unity-learning/src/systems/RunEngine.ts)

### 验收标准

- 玩家能感到“不同节点真在改变本局结构”。
- 异常节点不会被读成普通补给事件换皮。
- 节点差异不会破坏单局节奏和短局长度。

### 当前不该做

- 不扩复杂大地图。
- 不增加大量低价值节点类型。
- 不让异常节点退回纯数值补包。

## 工作流 5：表现与结果页收束

### 目标

让 HUD、面板、结果页把关键设计信息讲清楚，同时保持克制，不掩盖玩法问题。

### 为什么排第五

- 表现层很重要，但它应该服务已成立的玩法，而不是替玩法兜底。
- 当前阶段更适合收束信息结构，而不是大翻视觉主题。

### 具体任务

- 继续确认 HUD 是否只保留最关键的信息。
- 继续确认路线状态、阶段变化、当前目标是否一眼能读到。
- 继续确认结果页能清楚讲出“这局发生了什么、为什么想再开一局”。
- 继续确认音频和轻量反馈足以支撑即时游戏感。

### 主要落点

- [OverlayController.ts](/E:/codex/unity-learning/src/ui/OverlayController.ts)
- [ResultScene.ts](/E:/codex/unity-learning/src/scenes/ResultScene.ts)
- [GameScene.ts](/E:/codex/unity-learning/src/scenes/GameScene.ts)
- [PilotAudio.ts](/E:/codex/unity-learning/src/systems/PilotAudio.ts)
- [style.css](/E:/codex/unity-learning/src/style.css)

### 验收标准

- 玩家在战斗里能快速读懂局势，不需要靠额外说明。
- 结果页能帮助玩家理解本局路线与结尾，而不是只显示成绩。
- 表现层优化不会被误当成对玩法问题的掩盖。

### 当前不该做

- 不开纯 UI 主题翻修轮。
- 不用长文案解释所有机制。
- 不把 HUD 重新做重。

## 工作流 6：指标、复检与签收口径

### 目标

让每一轮设计优化都能被追踪、复检和签收，不依赖单次试玩印象。

### 为什么排第六

- 这是所有工作流的收口层。
- 没有统一签收口径，项目很容易在“感觉更好了”里失去方向。

### 具体任务

- 保持路线倾向、站稳、成型、转线、Boss 阶段等关键字段稳定可用。
- 根据当前主线补最小必要的 debug 字段，不让验证层膨胀成新系统。
- 保持 `build + full-flow + 定点样本` 的基础复检流程。
- 每轮开发后同步更新复盘、交接卡和待办。

### 主要落点

- [MetricsTracker.ts](/E:/codex/unity-learning/src/systems/MetricsTracker.ts)
- [测试与验证手册.md](/E:/codex/unity-learning/doc/30_持续优化/测试与验证手册.md)
- [版本目标与验收标准.md](/E:/codex/unity-learning/doc/20_设计闭环/版本目标与验收标准.md)
- [当前待办与优先级.md](/E:/codex/unity-learning/doc/30_持续优化/当前待办与优先级.md)

### 验收标准

- 每条主线都有可复检口径。
- 每轮开发都能明确回答“改了什么、为什么改、怎么验证、有没有回退”。
- 验证层只服务主线，不单独长成一轮工具开发。

### 当前不该做

- 不做 selector-only 调参轮。
- 不把所有问题都改写成指标问题。
- 不为了观测而增加大量和体验无关的埋点。

## 当前版本的建议排期

### P0：立刻推进

- 核心战斗回报链
- 三路线实战读感

### P1：跟进复检

- 精英与 Boss 收尾稳定性
- 指标、复检与签收口径

### P2：并行维护

- 节点与异常差异感
- 表现与结果页收束

## 任务拆解使用方式

- 做版本排期时，按“工作流”拆大块。
- 写开发任务时，按“具体任务”拆小项。
- 做签收时，按“验收标准”逐条复核。
- 做复盘时，按“为什么做 / 动了哪层 / 验收结果 / 是否回退”记录。
