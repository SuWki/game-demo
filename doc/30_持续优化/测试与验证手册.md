# 测试与验证手册

## 目标

确保每轮修改不是“感觉变好了”，而是有最小可重复验证。

## 最低验证要求

每次开发后至少完成：

1. `npm run build`
2. 一项与本轮问题直接相关的验证
3. 将验证结果写入开发复盘

## 常用验证方式

### 构建验证

- 命令：`npm run build`
- 作用：确认类型和构建没有坏

### 浏览器流程验证

- 目标：确认开始 -> 节点 -> 战斗 / 整备 / 异常 -> 首领 -> 结算 -> 重开 可跑通
- 参考历史脚本与结果：
  - `output/playwright/`

### 指标导出验证

- 页面内可通过：
  - `window.__pilotMetrics`
  - `window.__exportPilotMetrics()`
- 作用：确认局内状态和结果摘要是否被正确记录

### 战斗快照验证

- 页面内可通过：
  - `window.__pilotBattleDebug()`
- 作用：
  - 定向看当前是否处于 battle / elite / boss 样本
  - 辅助复检精英 `eliteRecoverySec / escortRecoveryCount` 这类裂口时机
  - 避免定向战斗截图完全依赖肉眼碰运气

### 专项验证

- 首领自然样本：
  - 参考 `output/qa/boss-pocket-natural-runs.mts`
- 首领阶段模式：
  - 参考 `output/qa/boss-phase-patterns.mts`
  - 参考 `output/qa/boss-phase-signatures.mts`
- 路线流程抽样：
  - 参考 `output/playwright/commitment-pacing/`

## 验证结果怎么写

开发复盘里必须写：

- 用了什么验证
- 结果是什么
- 结论是什么
- 还有什么没验证

## 当前注意事项

- `output/` 是验证资产和脚本区，不是项目事实源
- `tools/` 是辅助工具区，不应作为设计依据
- `progress.md` 是历史工作记录，不再作为当前真相入口

## 2026-04-25 稳定性与监控补充

### 新增监控字段

- 本轮起，`window.__pilotBattleDebug()` 与 `window.__exportPilotMetrics()` 会统一暴露以下字段：
  - `lateDashWindowMoments`
  - `dashCounterMoments`
  - `eliteCrackSeen`
  - `eliteCrackFollowThroughMoments`
  - `bossFirelineCoverage`
  - `bossSafeWindowMoments`
  - `killPickupContinueMoments`

### 字段使用口径

- `lateDashWindowMoments`：后段 `dash` 借窗兑现时刻数，用于判断自然流里后段 payoff 是否真的成立。
- `dashCounterMoments`：`dash` 换位后追回主动权的短窗口数，用于判断是否只是位移、还是已经形成回切反打。
- `eliteCrackSeen / eliteCrackFollowThroughMoments`：精英裂口是否形成、裂口后是否真正发生追本体承接。
- `bossFirelineCoverage / bossSafeWindowMoments`：`boss-bastion` 火线阶段的压迫覆盖率与安全窗生成次数。
- `killPickupContinueMoments`：普通战“击杀 -> 掉落 / 拾取 -> 继续开火”回报链的连续样本。

### 本轮后推荐的最小验证组合

1. `npm run build`
2. 一次自然 full-flow
3. 一次更长的自然样本复检
4. 一次定向精英裂口样本
5. 一次定向 Boss 火线样本

### 验证注意事项

- 如果自然长样本没有抽到目标路线，先记录为“样本不足”，不要直接误判成“玩法回退”。
- `RunEngine.tick()` 只在 `state.status === 'battle'` 时推进，所以定向验证脚本必须自动处理中途升级 / 事件面板，否则会把“战斗暂停”误读成“阶段没有推进”。
- 定向 Boss 火线复检允许使用：
  - debug 配置里的 `invulnerablePlayer`
  - `window.__pilotDebug.setPressureState()`
- 上述 debug 注入只服务验证，不属于正式玩法逻辑。

## 2026-04-26 游玩体验补强验证补充

### 文案与乱码扫描

每轮涉及 UI、toast、节点、升级、危险提示或结算文案时，必须至少执行一次：

```powershell
Select-String -Path 'src/**/*.ts','doc/**/*.md' -Pattern '\?\?\?|绮捐|瑁傚|鑻|�' -Encoding UTF8
```

发现玩家可见乱码时，本轮应优先修复；如果只是历史文档残留，也必须在复盘中说明是否处理。

### 手感观察项

体验补强轮至少观察：

- 移动起步、停手和反向转向是否更跟手。
- 自动开火与命中反馈是否能形成连续节奏。
- 击杀、掉落、吸附、拾取、升级是否形成清楚回报链。
- 受伤、擦弹、压力上升是否不会被击杀爽感盖掉。
- 节点 / 升级 / 结算页是否不用读长文也能理解。

### 推荐验证组合

1. `npm run build`
2. 一次自然 full-flow
3. 一次 3~5 分钟自然战斗样本，重点看普通战手感和音效层级
4. 一次音频 debug 快照，确认 `routeFocus / encounter / intensity` 仍正确
5. 一次文案截图或肉眼检查，确认开始页、HUD、升级页、结算页文字通俗可读

### 强化档位验证

- 命令：`npx tsx` 抽样执行 `buildUpgradeChoice(archetype, rarity)`。
- 作用：确认同一强化在 `common / uncommon / rare / epic / legendary` 五档之间不会大面积重合，尤其是 `pierce / multishot` 这种离散值。
- 关注点：看 `valueScore`、`effects` 和描述文本是否都随稀有度递增，避免“数字一样但档位不同”的假成长。
