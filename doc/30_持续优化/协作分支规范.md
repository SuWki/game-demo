# 协作分支规范

## 目标

避免在 AI 协作开发中分支策略失控，同时保留用户对正式分支的最终控制权。

## 当前原则

- `master` 只由用户手动合并和管理。
- AI 不直接决定长期分支策略。
- 如果用户没有明确要求切分支，默认在当前活动分支上完成本轮工作。
- 任何涉及分支整理、历史清理、强制同步的操作，都必须由用户明确确认后再做。

## 当前现实情况

- 仓库历史上出现过 `codex/*` 主题分支。
- 旧规则文档曾建议只保留 `master / codex / codex-dev`。
- 当前实际仓库状态未必严格遵守该旧规则，因此后续所有 Git 操作都应以“当前分支现状 + 用户明确指令”为准。

## 推荐执行方式

- 小范围修改：直接在当前活动分支完成。
- 需要独立主题时：由用户明确是否新开分支。
- 准备提交前：
  - 先确认哪些文件应该提交
  - 确认 `progress.md`、`output/`、`tools/` 是否应排除

## 不要做的事

- 不要默认清理所有 `codex/*` 分支
- 不要默认把开发内容合并到 `master`
- 不要在没有确认前重写用户现有 Git 习惯

## 当前执行口径（用户已明确）

- 常用长期分支只保留 `master / codex / codex-dev`。
- 后续日常开发默认继续在当前活动分支完成，不再为每一轮单独新开主题分支。
- `codex-dev` 可以作为当前开发分支，但目标是只比 `codex` 多出当前一轮需要保留的提交。
- `master` 仍只由用户手动合并和管理。
- 如果未来仓库里还残留旧的 `codex/*` 分支，它们不再作为默认开发入口；后续是否清理，仍由用户决定。
