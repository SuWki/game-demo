# 文档维护规则

## 当前文档分工

- `00_接手入口`
  当前真相入口
- `10_设计文档`
  当前有效设计
- `20_设计闭环`
  设计目标、验证方式、风险和阶段标准
- `30_持续优化`
  流程、验证、复盘和待办
- `40_AI协作`
  AI 接手协议和提示词模板
- `90_历史归档`
  旧阶段文档和历史记录

## Codex / Kimi 协作分工

从 `2026-04-28` 起，项目后续开发采用“双模型分工”：

- `Codex` 负责方向判断、设计规划、文档维护、素材与音效方案/预览产出、开发提示词编写、验收要求定义、文档变更提交与 Gitee 推送。
- `Kimi` 负责按 Codex 输出的开发提示词进行代码实现、构建验证、浏览器 QA、问题修复、代码提交与 Gitee 推送。
- 如果任务涉及图片素材、音效、预览板、素材清单、音频清单，默认由 `Codex` 先完成设计和资产草案，再交给 `Kimi` 接线或落地。
- 如果任务涉及 `src/` 代码修改，默认不由 `Codex` 直接修改代码，而是由 `Codex` 输出清晰的 Kimi 开发提示词。
- 如果用户明确要求 Codex 临时直接修代码，必须在本轮开始前重新确认范围；否则保持“Codex 不写代码，只写方向 / 文档 / 提示词”的默认规则。

### Codex 每轮必须做

- 读取并更新当前真实文档，不能只依赖聊天上下文。
- 明确下一轮开发目标、优先级、边界和验收方式。
- 如果要交给 Kimi 开发，输出可直接复制的中文提示词。
- 如果项目事实、阶段判断、风险、验收标准或素材/音效方案变化，必须同步 docs。
- 每次修改文档后，只暂存本轮相关文档，提交到当前开发分支，并尝试推送到 Gitee。

### Kimi 每轮必须做

- 严格按 Codex 提示词阅读指定文档和代码。
- 先输出理解与实施计划，再开始代码修改。
- 不重写主流程，不扩大系统边界，不擅自改设计方向。
- 完成后运行提示词要求的构建、QA 和专项验证。
- 同步更新必要复盘文档，只暂存本轮相关代码与文档，提交到当前开发分支，并尝试推送到 Gitee。

### Gitee 提交要求

- 当前远端仓库为 `origin = https://gitee.com/suwki/unity-learning.git`。
- Codex 每轮出完文档、规则、设计方案、素材/音效方案或 Kimi 提示词后，必须提交本轮文档变更，并尝试推送到 Gitee。
- Kimi 每轮开发完代码、QA 脚本或资源接线后，必须提交本轮代码和必要文档变更，并尝试推送到 Gitee。
- 提交前必须先检查 `git status`，只暂存本轮相关文件，不混入历史脏文件、`output/`、临时工具包或无关改动。
- 如 Gitee 推送失败，不能假装完成；必须在最终回复中说明失败原因、保留的本地 commit hash 和后续处理建议。
- 最终回复必须包含本轮 commit hash 和 Gitee 推送状态。

### 提示词交接原则

- Codex 给 Kimi 的提示词必须包含：目标、必读文档、必读代码、允许修改范围、禁止事项、验收方式、文档同步要求、最终回复格式。
- Kimi 不应根据聊天上下文猜项目现状，必须以仓库文档为准。
- 如果 Codex 与 Kimi 的结论冲突，以 `当前交接卡.md`、`设计基线与约束.md`、最新复盘和本轮提示词为准。

## 必须同步更新的场景

### 场景 1：本轮目标或风险变化

必须更新：

- `../00_接手入口/当前交接卡.md`
- `../20_设计闭环/风险与设计决策.md`

### 场景 2：设计边界变化

必须更新：

- 对应的 `../10_设计文档/*`
- `../20_设计闭环/设计基线与约束.md`

### 场景 3：阶段判断变化

必须更新：

- `../00_接手入口/当前交接卡.md`
- `../20_设计闭环/版本目标与验收标准.md`

### 场景 4：每次开发结束

必须新增：

- `开发复盘/` 下的新文档

## 不再作为当前事实源的文件

- `progress.md`
- `output/`
- `tools/`
- `../90_历史归档/旧版阶段文档/*`

这些文件仍可用于追溯，但不能替代当前真相文档。
