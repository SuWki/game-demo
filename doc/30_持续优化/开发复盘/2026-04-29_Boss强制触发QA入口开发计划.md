# 2026-04-29 Boss 强制触发 QA 入口开发计划

## 本轮判断

`2026-04-29_Boss精英专项样本补足与体验验收闭环.md` 已经把验收问题收窄：

- 精英样本已抓到 `elite-vice`，可证明精英至少具备行为差异。
- 素材黑底已通过截图检查，没有发现明显黑底或黑框。
- 音效层级已通过 debug 采样和 `PilotAudio` ducking 配置检查。
- Boss 实机样本仍然缺失，10 次重开未稳定触发 Boss。

因此下一轮不应继续泛化验收，也不应马上新增 Boss 或回调 Boss 数值。当前真正缺的是“稳定进入指定 Boss 的测试入口”。

## 下一步开发方向

下一轮交给 Kimi 的目标应是：补一个测试专用 Boss 强制触发入口，并用它完成 Boss 实机样本闭环。

核心原则：

- 这是 QA / debug 能力，不是玩家正式流程。
- 默认不影响普通游玩。
- 只做最小必要接口，不重写节点系统。
- 入口可以通过 query 参数、localStorage、debug 方法或 QA 脚本注入实现，优先选择对现有主流程侵入最小的方式。

## 推荐验收对象

优先级：

1. `boss-bastion`：适合验证安全窗、火线和屏卫压迫。
2. `boss-hunt`：适合验证正面压制和弹幕密度。
3. `boss-lockdown`：作为补充验证，成本高时可放到下一轮。

## 必须产出的证据

- `npm run build` 通过。
- 至少 1 个 Boss 被稳定触发。
- 至少 1 张 Boss 战截图。
- 至少 1 份 Boss debug JSON 或 summary。
- 记录 `bossSafeWindowMoments`。
- 记录 `bossFirelineCoverage`。
- 记录玩家受伤次数、Boss 战持续时间、结算状态和 console errors。
- 明确判断 Boss 是“高压但可读”“过密不可读”还是“压力不足”。

## 如果 Boss 验证失败

若 Boss 仍然不可读：

- 优先增加预警时间。
- 优先放大或延长安全窗。
- 优先减少连续封路时间。
- 不直接堆弹幕。

若 Boss 压力不足：

- 优先补阶段提示、攻击后反打窗口和路线答题点。
- 不直接把弹幕密度加回旧值。

若 QA 入口污染正式流程：

- 必须回退或隔离入口。
- 入口只允许在测试参数或 debug flag 下生效。

## 本轮不建议做

- 不新增 Boss。
- 不新增精英。
- 不继续调精英参数。
- 不重写 `RunEngine`。
- 不重开节点主流程。
- 不把 QA 入口变成玩家正式功能。
- 不继续用自然随机路线碰 Boss。
