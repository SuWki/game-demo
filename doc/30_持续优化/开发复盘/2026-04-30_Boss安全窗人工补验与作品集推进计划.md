# 2026-04-30 Boss 安全窗人工补验与作品集推进计划

## 本轮判断

Kimi 已完成 Boss 强制触发 QA 入口与 Boss 实机样本闭环：

- `window.__pilotQaForceBoss(templateId)` 已支持 `boss-bastion`、`boss-hunt`、`boss-lockdown`。
- `boss-bastion` 和 `boss-hunt` 均可通过 QA 脚本稳定触发。
- `npm run build` 和 `qa-current-version.mjs` 已通过。
- Boss 战截图显示基础画面可读。
- 但 headless QA 因帧率限制，`bossSafeWindowMoments` 未能在采样时间内积累到非零。

因此当前不需要继续扩大 QA 系统，也不应该直接修改 Boss 数值。下一步应做一次真实浏览器人工补验，确认安全窗是否被玩家实际看见。

## 下一步开发方向

下一轮目标不是“开发新功能”，而是“人工实机补验 + 作品集推进判断”。

优先顺序：

1. 在浏览器中调用 `window.__pilotQaForceBoss('boss-bastion')`。
2. 观察 60~90 秒 Boss 战。
3. 截取安全窗、弹幕墙、Boss 压迫画面。
4. 判断 Boss 是可签收、过密不可读，还是压力不足。
5. 如果可签收，进入作品集 Boss 案例页、短视频脚本和素材音效 A/B 展示。
6. 如果不可签收，再交给 Kimi 做小步 Boss 修复。

## 签收标准

Boss 可以签收时，应满足：

- 玩家能看见弹幕缺口或安全窗。
- Boss 有压迫感，但不会连续封死玩家移动空间。
- 玩家有机会移动、躲避、反打。
- 截图能用于作品集说明“高压但可读”。
- `__pilotQaForceBoss` 不影响普通 full-flow。

如果 Boss 不可签收：

- 若过密：优先增大安全窗、延长预警、减少连续封路时间。
- 若过弱：优先补阶段提示、攻击后反打节奏或路线答题点。
- 不直接新增 Boss，不重写主流程，不大幅加回弹幕密度。

## 作品集衔接

若 Boss 人工补验通过，下一阶段进入作品集材料整理：

- Boss 战案例页补截图标注。
- 编写 30~60 秒 Boss 战短视频脚本。
- 说明 `crit / pierce / dash` 三路线在 Boss 压力下的答题方式。
- 整理素材和音效 A/B 对比：旧程序化表现 vs 当前接入素材/音效。
- 保留 QA 数据作为设计依据，不把 AI 协作过程当作主要卖点。

## 本轮不建议做

- 不新增 Boss。
- 不新增精英。
- 不继续扩路线内容池。
- 不重写 `RunEngine`。
- 不扩大 QA 系统。
- 不做全量素材替换。
- 不做大规模 UI 重做。
