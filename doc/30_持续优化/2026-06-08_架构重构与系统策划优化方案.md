**创建日期**: 2026-06-08  
**状态**: 待开发  
**优先级**: P0 - 技术债清理

## 一、当前项目核心问题

### 1.1 巨型文件 / God Object

| 文件 | 大小 | 行数 | 问题 |
|------|------|------|------|
| `src/systems/RunEngine.ts` | **390KB** | ~10000+ | 承担战斗模拟、AI、生成、升级、路线判定等所有逻辑 |
| `src/scenes/GameScene.ts` | **212KB** | ~5000+ | 渲染 + 输入 + UI + 特效 + 部分逻辑全部混在一起 |
| `src/style.css` | **119KB** | - | DOM UI 样式堆积，无模块化 |
| `src/data/upgrades.ts` | **82KB** | 3449 | 所有升级定义硬编码在一个文件 |
| `src/game/types.ts` | **26KB** | 903 | 全局类型大杂烩 |

**影响**: 无法维护、无法协作、无法定位问题、编译缓慢。

### 1.2 逻辑层与渲染层耦合

- `RunEngine` 本应是纯逻辑层，但 `GameScene` 里仍有大量直接操作 `BattleState` 的代码
- 视觉指示器、状态追踪变量（`lastDashDriveSec`、`lastTurnBurstSec` 等）散落在渲染层
- 渲染层不应持有战斗状态副本

### 1.3 数据不是真正可配置的

- `balance.ts`、`upgrades.ts`、`battleTemplates.ts` 里的数值全部硬编码在 TypeScript 中
- 虽有 `excel:to-json` 工具，但实际运行时仍依赖 TS 常量
- **策划无法独立调参**，每次改数值都要改代码、重新构建

### 1.4 缺少组件化 / ECS 思维

- 当前是 "一个大 State 对象 + 几个巨型 System" 模式
- 敌人行为、子弹系统、路线被动、连杀系统全部塞在 `RunEngine` 里
- 没有拆分为独立组件，无法独立测试和复用

### 1.5 测试覆盖不足

- `src/tests/` 下只有 `balance_test.ts`
- 核心战斗逻辑（`RunEngine` 390KB）没有任何单元测试
- 平衡性验证全靠手工目测和 QA smoke 脚本

### 1.6 魔法数字散落

- 虽有 `balance.ts` 做集中管理，但 `RunEngine` 和 `GameScene` 中仍有大量硬编码常量
- 如 `0.3`、`1.2`、`80`、`120` 等，没有统一引用

### 1.7 大量 if-else 分支

- `RunEngine` 中存在大量 `if (routeId === 'crit') { ... } else if (routeId === 'pierce') { ... }` 分支
- 新增路线或修改逻辑需要改动多处，违反开闭原则

## 二、优化方案

### 2.2 引入接口与策略模式（P0）

```typescript
// src/systems/route/IRoutePassive.ts
export interface RoutePassiveContext {
  battle: BattleState;
  run: RunState;
  dt: number;
}

export interface HitContext extends RoutePassiveContext {
  damage: number;
  isCrit: boolean;
  target: EnemyState;
}

export interface KillContext extends RoutePassiveContext {
  enemy: EnemyState;
  wasCrit: boolean;
  wasPierce: boolean;
  wasDash: boolean;
}

export interface IRoutePassive {
  readonly routeId: RouteId;
  onHit(ctx: HitContext): void;
  onKill(ctx: KillContext): void;
  onUpdate(ctx: RoutePassiveContext): void;
  getVisualState(battle: BattleState): RouteVisualState;
}

// 使用：RouteManager 持有 IRoutePassive[] 数组，统一调度
```

### 2.3 事件系统解耦（P1）

```typescript
// src/systems/events/EventBus.ts
export type GameEvent = 
  | { type: 'enemy:killed'; enemy: EnemyState; killer: 'player'; wasCrit: boolean }
  | { type: 'player:hit'; damage: number; source: EnemyState }
  | { type: 'upgrade:applied'; upgrade: UpgradeDefinition }
  | { type: 'route:matured'; routeId: RouteId };

export interface IEventBus {
  emit<E extends GameEvent>(event: E): void;
  on<E extends GameEvent>(type: E['type'], handler: (event: E) => void): () => void;
}

// 各系统通过事件通信，而非直接调用
```

## 四、验收标准

1. **构建通过**: `npm run build` 无错误
2. **类型检查通过**: `tsc --noEmit` 无错误
3. **功能回归**: 现有 QA smoke 场景全部通过
4. **文件大小**: 单文件不超过 100KB / 3000行
5. **可配置性**: 策划可仅修改 JSON 文件调整数值
6. **可测试性**: 核心子系统有独立单元测试

---

## 五、风险提示

1. **拆分风险**: `RunEngine` 内部耦合严重，拆分时需要仔细梳理依赖关系
2. **回归风险**: 大规模重构可能引入隐藏 bug，需要充分的 smoke 测试
3. **性能风险**: 运行时加载 JSON 可能影响启动速度，需要考虑预加载策略
4. **协作风险**: 如果有其他分支在开发，合并冲突会很大
