# AI 接手协议

## 目标

让任何新的 GPT / Codex 接手时，不依赖聊天上下文，只依赖仓库文档也能继续工作。

## 当前协作模式：Codex 规划，Kimi 开发

从 `2026-04-28` 起，默认协作方式调整为：

- `Codex` 不再默认直接修改代码；Codex 负责制定方向、更新设计/规则/复盘文档、产出图片素材和音效草案、编写 Kimi 开发提示词。
- `Kimi` 负责代码落地；当任务需要修改 `src/`、构建工具、QA 脚本或运行时代码时，应由 Kimi 按 Codex 提示词实施。
- `Codex` 可以修改 docs、素材设计文档、音效设计文档、协作规则文档，并在每轮完成后提交 Git 且尝试推送到 Gitee。
- 如果用户明确要求 Codex 直接写代码，本轮必须先重新确认；否则保持“只做方向和文档”的默认边界。
- Kimi 完成开发后，Codex 可以继续做验收判断、文档补全、下一轮计划和新的 Kimi 提示词。

## 执行规则

- 不要因为仓库名误判技术栈。
- 不要在没有明确目标时直接重构。
- 不要同时开启多个主题。
- 不要引用历史归档替代当前真相。
- 输出默认使用中文。
- 如果使用代码字段，可在括号里保留英文对照。
- 每次实际修改代码或文档前，先确认当前分支是否为 `codex-dev`。
- 每次实际修改完成后，必须先提交到 `codex-dev`，并尝试推送到 Gitee；不要直接把最新一轮开发推到 `codex`。
- `codex` 分支默认视为上一轮稳定基线，必须始终比 `codex-dev` 少一次 commit，除非用户明确要求同步。
- 如果 Gitee 推送失败，必须在最终回复中说明失败原因、保留本地 commit hash，并给出下一步处理建议。

## 每次开发必须产出

- 一份新的开发复盘文档
- 更新后的 `当前交接卡.md`
- 如果设计有变化，更新对应设计文档
- 如果阶段判断变化，更新版本目标文档和风险文档

## 禁止事项

- 禁止只改代码不改文档
- 禁止只看 `progress.md` 判断项目
- 禁止把 `output/` 和 `tools/` 当作事实源
