# AI 接手协议

## 目标

让任何新的 GPT / Codex 接手时，不依赖聊天上下文，只依赖仓库文档也能继续工作。

## 当前协作模式：Codex 规划，Kimi 开发

从 `2026-04-28` 起，默认协作方式调整为：

- `Codex` 不再默认直接修改代码；Codex 负责制定方向、更新设计/规则/复盘文档、产出图片素材和音效草案、编写 Kimi 开发提示词，并在提示词中给出代码骨架草案。
- `Kimi` 负责代码落地；当任务需要修改 `src/`、构建工具、QA 脚本或运行时代码时，应由 Kimi 按 Codex 提示词和代码骨架草案实施。
- `Codex` 可以修改 docs、素材设计文档、音效设计文档、协作规则文档，并在每轮完成后提交 Git，且必须同时尝试推送到 Gitee 和 GitHub。
- 如果用户明确要求 Codex 直接写代码或先写真实 scaffold，本轮必须先重新确认；否则保持“只做方向、文档、提示词和代码骨架草案”的默认边界。
- Kimi 完成开发后，Codex 可以继续做验收判断、文档补全、下一轮计划和新的 Kimi 提示词。

## 2026-05-03 当前工作流摘要

后续对话接手时，默认按以下循环推进：

1. 用户提出体验问题或开发方向。
2. Codex 读取当前文档，判断真实进度，更新规则 / 设计 / 交接文档。
3. Codex 输出给 Kimi 的任务卡或完整提示词，包含文件级导航、代码骨架、伪代码、验收标准和提交要求。
4. Kimi 负责代码落地、构建、QA、复盘、提交和推送；凡是实际产生代码改动，完成后必须同步提交并推送到 Gitee 和 GitHub。
5. 用户把 Kimi 回复交给 Codex。
6. Codex 复验 Kimi 结果，不只看汇报；必要时抽查 diff、补跑 QA、补文档、补提交。
7. Codex 判断下一轮是实机验收、继续开发、还是文档整理。

当前推荐下一轮主题：

- `流派构筑第三轮 + 路线表现迁移到敌人受击层`。
- 这轮重点不是素材扩展，也不是作品集，而是让 `crit / pierce / dash` 从数值叠加变成可构筑、可读、可验证的战斗体验。

当前仍未完成：

- 真正的品质联动构筑。
- 路线触发表现从文字 / 玩家周围线条迁移到敌人受击特效。
- 三路线各一局实机验收。
- Boss 胜利路径收尾节奏确认。
- 敌人状态标记可读性确认。

## 执行规则

- 不要因为仓库名误判技术栈。
- 不要在没有明确目标时直接重构。
- 不要同时开启多个主题。
- 不要引用历史归档替代当前真相。
- 输出默认使用中文。
- 无论用户临时使用英文、开发回传使用英文，还是工具日志中夹带英文，Codex 面向用户的最终回复都必须默认使用中文；只有在用户明确要求“改用英文回复”时，才允许切换主要叙述语言。
- 如果使用代码字段，可在括号里保留英文对照。
- Kimi / 开发 GPT 可以在执行过程中保留英文命令输出、代码字段、工具日志和临时草稿，但开始前判断、实施计划、验证结论、开发复盘和最终汇报必须使用中文。
- 如果开发回传内容是英文，Codex 在验收和转述时必须先整理成中文，再继续给用户下一轮结论、提示词或验收判断，不能直接沿用英文叙述口径。
- 如果用户用编号列出问题，下一次最终汇报必须逐条复述用户原问题，并给出对应解决方案、完成状态和未完成原因；禁止只总结“本轮做了什么”。
- 如果 Kimi 回复没有逐条回应用户原问题，Codex 必须要求补全或在验收文档中补齐，不能直接签收。
- 如果 Kimi 只提交代码没有提交文档，Codex 必须视为流程未完成，补文档或要求返工。
- 如果 Codex 自己更新了文档或规则，也必须提交并同时尝试推送到 Gitee 和 GitHub。
- 每次实际修改代码或文档前，先确认当前分支是否为 `codex-dev`。
- Codex 默认不修改真实代码文件；如需提速 Kimi，应优先在提示词中提供文件级修改计划、接口草案和关键伪代码。
- Codex 只有在用户明确要求时，才允许写最小真实 scaffold；scaffold 必须默认不改变玩家体验，并且不得覆盖未提交代码改动。
- 每次实际修改完成后，必须先提交到 `codex-dev`，并同时尝试推送到 Gitee 和 GitHub；不要直接把最新一轮开发推到 `codex`。
- `codex` 分支默认视为上一轮稳定基线，必须始终比 `codex-dev` 少一次 commit，除非用户明确要求同步。
- 如果 Gitee 或 GitHub 任一推送失败，必须在最终回复中说明失败原因、保留本地 commit hash，并给出下一步处理建议。

## 每次开发必须产出

- 一份新的开发复盘文档
- 更新后的 `当前交接卡.md`
- 如果设计有变化，更新对应设计文档
- 如果阶段判断变化，更新版本目标文档和风险文档

## 禁止事项

- 禁止只改代码不改文档
- 禁止只看 `progress.md` 判断项目
- 禁止把 `output/` 和 `tools/` 当作事实源
