# Codex 统一开发提示词规则模板

## 文档目的

这份模板用于统一后续给 Codex 的开发提示词结构。

目标是让以后每一轮提示词都满足：

- 先读文档，再动手
- 先说清本轮目标，再改代码
- 先给边界，再给任务
- 先给验证，再给交付
- 统一分支纪律与提交纪律

这份模板不是某一轮的专项提示词，而是以后所有开发提示词都应尽量遵守的**总模板**。

## 使用方式

以后要给 Codex 新提示词时，优先以本模板为骨架：

1. 保留固定规则部分
2. 替换本轮项目状态和本轮目标
3. 补充本轮允许做 / 不允许做的事
4. 补充本轮输出格式

如果有专项任务，例如 UI、美术、音频、战斗手感、Boss、数值平衡，可以在本模板基础上追加专项要求，但不要跳过本模板的核心约束。

## 固定模板

下面这段可以直接复制使用。

```md
你现在接手的是本项目当前这一轮开发任务。

注意：

- 你必须先读取当前有效文档，再开始判断和实施。
- 不要依赖聊天上下文猜项目历史。
- 不要把历史归档当成当前真相。
- 不要在没有明确本轮目标前直接重构或扩系统。

## 一、开始前必须先读文档

先按以下顺序阅读：

1. `doc/00_接手入口/START_HERE.md`
2. `doc/00_接手入口/当前交接卡.md`
3. `doc/00_接手入口/项目总览.md`

5. `doc/20_设计闭环/设计基线与约束.md`

7. `doc/20_设计闭环/玩法假设与验证闭环.md`
8. `doc/20_设计闭环/风险与设计决策.md`
9. `doc/30_持续优化/当前待办与优先级.md`
10. `doc/30_持续优化/测试与验证手册.md`
11. `doc/30_持续优化/开发复盘/` 下最新一篇文档
12. 本轮相关 `doc/10_设计文档/*`
13. 如果任务涉及 UI / 美术 / 音频 / AI 协作，额外阅读 `doc/40_AI协作/*` 下对应文档

如果文档之间存在阶段口径差异，请以：

1. `当前交接卡`
2. `设计基线与约束`
3. `版本目标与验收标准`
4. 最新开发复盘

为准，并在输出中说明你的取舍依据。

## 二、读完后先输出判断，再开始改

开始编码前，必须先用中文输出：

1. 你理解的当前项目是什么
2. 当前阶段是什么
3. 当前主问题是什么
4. 本轮目标是什么
5. 本轮明确不做什么
6. 你准备先看哪些代码文件
7. 你准备修改哪些文件
8. 你准备怎么验证

在这一步完成前，不要直接改代码。

【这里替换成每一轮的具体目标、问题、优先级和任务要求】

## 四、本轮允许做的事

【这里明确写允许优先处理的内容】

## 五、本轮不允许做的事

【这里明确写本轮禁止项】

## 六、文档同步要求

本轮不只是改代码，也必须同步更新 docs。

至少要求：

- 更新 `doc/00_接手入口/当前交接卡.md`
- 新增一篇本轮开发复盘到 `doc/30_持续优化/开发复盘/`
- 如果设计边界变化，更新 `doc/10_设计文档/*`
- 如果阶段判断、风险点、验收标准变化，更新 `doc/20_设计闭环/*`

如果本轮没有文档更新，必须在输出中说明为什么不需要更新。

## 七、Git 与分支规则（硬约束）

本项目默认开发分支为：`codex-dev`

固定规则：

1. 每次开始前先执行 `git branch --show-current`
2. 如果当前不在 `codex-dev`，先切到 `codex-dev`
3. 每次修改完代码或文档后，必须提交到 `codex-dev`
4. 每轮结束后至少执行：
   - `git status`
   - `git add <本轮相关文件>`
   - `git commit -m "<本轮主题>"`
   - `git push origin codex-dev`

额外分支纪律：

- `codex` 分支永远要比 `codex-dev` 少一次 commit
- 不要把当前最新一轮开发直接推到 `codex`
- 不要让 `codex` 和 `codex-dev` 指向同一个最新提交
- `codex` 视为“上一轮稳定基线”，`codex-dev` 视为“当前开发前沿”
- 除非用户明确要求，否则不要主动把 `codex` 追平到 `codex-dev`

如果 push 失败，必须在输出中明确说明。

## 八、验证要求

至少执行并汇报：

1. `npm run build`
2. 与本轮任务相关的流程验证
3. 说明有没有回退主流程、路线读感、Boss 收尾或当前监控项

如果本轮无法完成某项验证，必须说明原因。

## 九、输出要求

最终请至少输出：

1. 你理解的本轮目标
2. 你实际修改了哪些文件
3. 你实际解决了什么问题
4. 你如何验证
5. 哪些 docs 被同步更新
6. 当前还剩什么风险
7. 本轮最终所在分支是不是 `codex-dev`
8. 本轮最终 commit message 是什么
9. 是否已经成功 push 到 `origin/codex-dev`

## 十、核心原则

- 每轮只解决一个主问题
- 先守当前主线，再谈新主题
- 先做可验证、可回归的改动
- 不要用大改掩盖判断不清
- 不要只改代码不改文档
- 不要让开发节奏脱离当前阶段判断
```

## 使用建议

如果以后要写专项提示词，推荐按下面方式组合：

- 通用轮：本模板 + 本轮目标
- 战斗手感轮：本模板 + 战斗手感专项要求
- UI / 美术轮：本模板 + UI / 美术专项要求
- 音频轮：本模板 + 音频专项要求
- 数值 / 平衡轮：本模板 + 数值公式与验证要求

这样可以保证提示词再怎么换主题，也不会丢掉文档纪律、验证纪律和分支纪律。
