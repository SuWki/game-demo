# Codex / Kimi 协作分工规则

2. `doc/00_接手入口/当前交接卡.md`
3. `doc/30_持续优化/当前待办与优先级.md`

6. `doc/40_AI协作/Kimi任务卡模板.md`
7. `doc/30_持续优化/开发复盘/` 下最新一篇相关复盘

## Codex 每轮输出格式

Codex 给用户或给 Kimi 前，默认按以下结构输出：

1. 当前真实判断：哪些已完成、哪些不能签收、当前最大风险是什么。
2. 本轮目标：只选 1 个主目标，最多 2 个辅助目标。
3. 文件级导航：告诉 Kimi 需要看哪些文件、为什么看。
4. 大体框架：说明要改的模块、数据流、接口边界。
5. 关键伪代码：只写骨架，不默认改真实代码。
6. 验收标准：必须包含构建、QA、实机观察点和不能提交 `output/qa`。
7. 文档同步要求：必须更新交接卡、待办、设计文档或复盘。
8. 提交要求：只暂存本轮相关文件，提交并推送 Gitee。

如果用户列了编号问题，Codex 的下一次最终回复必须逐条回应：

- 问题：复述用户原问题。
- 方案：本轮准备怎么解决或已经怎么解决。
- 状态：已完成 / 待验收 / 本轮不做及原因。

## Kimi 每轮输出格式

Kimi 最终回复必须全中文，并按以下结构：

1. 本轮目标。
2. 用户原问题逐条回应：每条都写“问题 / 解决方案 / 当前状态”。
3. 开始前判断：当前阶段、最大风险、本轮不做什么。
4. 实际修改文件。
5. 关键实现说明。
6. 验证结果：至少 `npm run build`，以及 Codex 提示词指定 QA。
7. 文档更新。
8. commit hash。
9. Gitee push 状态。
10. 最大残留风险和下一步建议。

Kimi 允许命令输出、代码字段、文件名使用英文；但判断、计划、复盘和最终汇报必须中文。

## 每轮验收与提交红线

- `output/qa/`、临时截图、浏览器 summary 默认不提交，只在文档里记录关键结论。
- `.claude/settings.json`、个人配置、无关本地文件不提交。
- 禁止 `git add .`；必须逐个列出本轮相关文件。
- 代码开发完成但未更新文档，不能视为完成。
- 文档更新完成但未提交 Gitee，不能视为完成。
- Codex 验收 Kimi 回复时，不能只看汇报，要抽查 diff、跑关键验证，并补齐文档。

## 2026-05-02 复验补充：QA 产物提交红线

- `output/qa/` 下的截图、summary、浏览器样本、临时观测文件默认只能作为本地验证证据，不允许随代码或文档提交。
- 如任务需要保留 QA 证据，优先把关键数字、截图文件名和结论写入 `doc/30_持续优化/开发复盘/`，不要提交整批截图。
- 只有用户明确要求“提交 QA 截图/样本/展示资产”时，才允许暂存 `output/qa/` 内指定文件。
- Kimi 和 Codex 提交前都必须执行 `git status --short`，确认没有误暂存 `output/qa/`、临时文件或无关改动。
- 如果误提交了 `output/qa/`，下一轮必须在复盘里记录为流程问题，并优先修正提交习惯；未经用户要求不要用重写历史方式删除已推送提交。

## 2026-05-03 用户问题对齐规则

- 当用户明确列出问题并要求修改时，下一次 Codex 或 Kimi 的最终汇报必须逐条带回“用户原问题”和“对应解决方案 / 当前状态”。
- 不允许只写“本轮完成内容”，却不回答用户提出的每一个编号问题。
- 如果某个问题本轮没有解决，必须写清原因、阻塞点、下一步处理文件和验收方式。
- 如果用户提出的是设计理解问题，必须先给当前代码真实判断，再说明本轮能做的小修和后续需要的大重构，不能把“已分层命名”包装成“已经完成构筑玩法”。
- 复盘文档也要保留同样结构，方便下一个对话不依赖聊天上下文继续验收。

## 2026-05-10 游戏内文案去设计语规则

- 游戏运行时不允许出现给开发/策划看的设计性语言，例如“主路线信号”“承接”“补属性”“走流派”“还没有主流派”“构筑调整”“阶段行动开始”等。
- 游戏内文字只保留玩家能立刻执行或理解的内容，例如“开始游戏”“奖励倒计时”“击败 Boss”“进入安全区”“通关奖励”“精英”等。
- 如果某个概念需要解释，优先放在术语浮动框或文档中；不要放在战斗 HUD、toast、卡牌底部标签或关卡开始提示里。
- 升级卡底部不再放内部分类标签。卡牌只展示名称、效果、流派/稀有度徽章和必要的奖励来源。
- 表现层优先用敌人受击、弹道、短音效和短特效表达路线触发；不要恢复玩家周围常驻线条、路线仪表盘、无意义圆环或大段说明文字。

## 一句话规则

后续默认由 `Codex` 做方向、设计、素材/音效草案、代码骨架草案、文档和开发提示词，由 `Kimi` 做代码实现、构建验证和实机 QA。

## Codex 负责什么

- 判断下一步开发方向。
- 整理和更新项目文档。
- 写清开发边界、验收标准和风险。
- 产出图片素材、音效、预览板、素材清单和接线说明。
- 给 Kimi 输出可直接执行的开发提示词。
- 在提示词中给出代码大致框架、接口草案、文件改动顺序和关键伪代码，帮助 Kimi 快速落地。
- Kimi 开发完成后，继续做设计验收、文档补全和下一轮计划。
- 每次修改文档后，只暂存本轮相关文档，提交到当前开发分支，并尝试推送到 Gitee。

## Codex 默认不做什么

- 不默认直接修改 `src/` 代码。
- 不默认替 Kimi 做代码落地。
- 不默认创建或修改真实代码文件；代码骨架优先写在提示词中，作为 Kimi 的实现蓝图。
- 不在没有用户明确要求时重写系统、改主流程或修运行时代码。
- 不把聊天上下文当成唯一事实来源，必须同步当前 docs。

## Codex 代码骨架输出规则

- 默认模式：Codex 在 Kimi 提示词里给出“文件级修改计划 + 接口草案 + 关键伪代码 + 验收点”，不直接改 `src/`。
- 轻量 scaffold 模式：只有用户明确要求“Codex 先写代码骨架 / 先建文件 / 先搭接口”时，Codex 才能做最小真实代码改动。
- 轻量 scaffold 只允许做低风险结构：类型声明、空函数、debug helper 外壳、QA 脚本骨架、TODO 标记和不改变默认行为的开关。
- 轻量 scaffold 不允许包含完整业务逻辑、数值改动、战斗规则改写、主流程重构或会影响玩家体验的默认开启行为。
- 如果 Codex 写了真实代码骨架，必须在提示词中明确告诉 Kimi：哪些文件是 Codex scaffold、哪些 TODO 必须补完、哪些地方不能推翻重写。
- 如果工作区已有 Kimi 或用户未提交代码改动，Codex 默认不写真实代码骨架，改为只输出提示词骨架，避免冲突。

## Kimi 负责什么

- 严格按 Codex 提示词读取指定文档和代码。
- 优先沿着 Codex 给出的代码骨架草案补全实现；如需偏离骨架，必须在回复中说明原因。
- 工作过程中允许使用英文作为内部思考、代码注释草稿、命令输出摘录或工具日志语言，但面向用户的关键输出必须使用中文。
- Kimi 的开始前判断、实施计划、阶段性结论、验证结论、开发复盘和最终回复必须使用中文；除代码、命令、文件名、字段名、commit hash、工具原始输出外，不允许用英文作为主要叙述语言。
- 输出自己的理解、当前问题判断、实施计划。
- 修改代码、资源接线、构建脚本或 QA 脚本。
- 运行 `npm run build` 和提示词指定的 QA。
- 修改必要文档和新增开发复盘。
- 只暂存本轮相关代码和文档，提交到当前开发分支，并尝试推送到 Gitee。

## Kimi 默认不做什么

- 不擅自扩系统。
- 不重写 `RunEngine` 或主流程，除非提示词明确允许。
- 不用自己的判断覆盖当前设计基线。
- 不只改代码不改文档。
- 不把 `output/`、`progress.md` 或历史归档当成当前真相。

## 标准交接流程

1. 用户提出方向、问题或体验目标。
2. Codex 读取当前文档，判断下一轮优先级。
3. Codex 更新必要规则/设计/交接文档。
4. Codex 优先输出轻量任务卡；只有阶段切换或复杂任务才输出完整长提示词。
5. Kimi 按提示词开发、验证、提交。
6. 用户把 Kimi 回复给 Codex。
7. Codex 做验收判断，更新文档并决定下一轮方向。

## 轻量任务卡规则

- 默认优先使用 `doc/40_AI协作/Kimi任务卡模板.md`，只填写本轮变化项，减少重复上下文。
- 任务卡必须包含：一句话目标、最少必读文档、文件级导航、代码骨架草案、先验证后修复规则、验收命令、提交要求。
- 如果本轮只是补验、截图、QA 或小修，Codex 不再重复项目完整背景，只引用当前交接卡和最新复盘。
- 如果本轮涉及阶段切换、系统边界变化、玩法方向变化，才使用完整提示词。

## 文件级导航规则

- Codex 给 Kimi 的任务卡应尽量限定“本轮只需要看的文件”，避免 Kimi 每次读完整仓库。
- 文件级导航需要说明每个文件为什么要看，例如“`GameScene.ts`：Boss debug 入口接线”“`PilotAudio.ts`：cue ducking 层级”。
- 如果 Kimi 在执行中发现需要额外文件，必须在回复里说明原因。

## 先验证后修复规则

- 默认先跑验证，再决定是否改代码。
- 如果验证通过，只更新文档、截图索引或作品集材料，不强行改代码。
- 如果验证失败，只修失败项，不扩大成系统重构。
- Codex 给任务卡时应明确“通过时做什么”和“失败时允许修什么”。

## Gitee 提交规则

- 当前远端仓库为 Gitee：`origin = https://gitee.com/suwki/unity-learning.git`。
- Codex 每次完成文档、规则、设计、素材/音效方案或提示词沉淀后，必须执行一次 Git 提交，并在条件允许时推送到 Gitee。
- Kimi 每次完成代码开发、QA 脚本、资源接线或运行时修复后，必须执行一次 Git 提交，并在条件允许时推送到 Gitee。
- 提交前必须检查 `git status`，只暂存本轮相关文件，不混入历史脏文件、`output/`、临时文件或无关改动。
- 禁止使用 `git add .` 或等价的全量暂存命令；必须逐个列出本轮相关文件路径。
- 默认不提交 `output/` 下的 QA 截图、summary、临时样本或浏览器产物；除非任务明确要求“提交展示资产/截图索引”，否则这些文件只可作为本地验证证据。
- 如果当前分支不是 `codex-dev`，必须先确认是否切换；不要直接把开发提交推到 `codex` 稳定基线。
- 如果 Gitee 推送失败，必须保留本地 commit，并在最终回复里明确说明失败原因和当前 commit hash。
- Codex 最终回复必须说明本轮提交号和推送状态；Kimi 最终回复也必须说明本轮提交号和推送状态。

## Kimi 提示词必须包含

- 明确要求“过程可用英文记录工具/代码细节，但开始前判断、开发复盘和最终汇报必须中文输出”。
- 本轮目标。
- 必读文档。
- 必读代码。
- 当前问题判断。
- 允许修改范围。
- 明确不允许做的事。
- 体验验收标准。
- 构建和 QA 要求。
- 文档同步要求。
- 最终回复格式。

## 当前推荐节奏

- Codex 轮：方向规划、文档整理、素材/音效预览、Kimi 提示词、Gitee 提交。
- Kimi 轮：代码开发、构建、QA、复盘、Gitee 提交。
- Codex 轮：验收 Kimi 结果、补文档、定下一轮。
