# Codex / Kimi 协作分工规则

## 一句话规则

后续默认由 `Codex` 做方向、设计、素材/音效草案、代码骨架草案、文档和开发提示词，由 `Kimi` 做代码实现、构建验证和实机 QA。

## Codex 负责什么

- 判断下一步开发方向。
- 整理和更新项目文档。
- 写清开发边界、验收标准和风险。
- 产出图片素材、音效、预览板、素材清单和接线说明。
- 给 Kimi 输出可直接执行的开发提示词。
- 在提示词中给出代码大致框架、接口草案、文件改动顺序和关键伪代码，帮助 Kimi 快速落地。
- Kimi 开发完成后，继续做设计验收、文档补全和下一轮计划。
- 每次修改文档后，只暂存本轮相关文档，提交到当前开发分支，并尝试推送到 Gitee。

## Codex 默认不做什么

- 不默认直接修改 `src/` 代码。
- 不默认替 Kimi 做代码落地。
- 不默认创建或修改真实代码文件；代码骨架优先写在提示词中，作为 Kimi 的实现蓝图。
- 不在没有用户明确要求时重写系统、改主流程或修运行时代码。
- 不把聊天上下文当成唯一事实来源，必须同步当前 docs。

## Codex 代码骨架输出规则

- 默认模式：Codex 在 Kimi 提示词里给出“文件级修改计划 + 接口草案 + 关键伪代码 + 验收点”，不直接改 `src/`。
- 轻量 scaffold 模式：只有用户明确要求“Codex 先写代码骨架 / 先建文件 / 先搭接口”时，Codex 才能做最小真实代码改动。
- 轻量 scaffold 只允许做低风险结构：类型声明、空函数、debug helper 外壳、QA 脚本骨架、TODO 标记和不改变默认行为的开关。
- 轻量 scaffold 不允许包含完整业务逻辑、数值改动、战斗规则改写、主流程重构或会影响玩家体验的默认开启行为。
- 如果 Codex 写了真实代码骨架，必须在提示词中明确告诉 Kimi：哪些文件是 Codex scaffold、哪些 TODO 必须补完、哪些地方不能推翻重写。
- 如果工作区已有 Kimi 或用户未提交代码改动，Codex 默认不写真实代码骨架，改为只输出提示词骨架，避免冲突。

## Kimi 负责什么

- 严格按 Codex 提示词读取指定文档和代码。
- 优先沿着 Codex 给出的代码骨架草案补全实现；如需偏离骨架，必须在回复中说明原因。
- 全程使用中文输出，包括开始前判断、实施计划、验证结论、开发复盘和最终回复；除代码、命令、文件名、字段名外，不使用英文作为主要叙述语言。
- 输出自己的理解、当前问题判断、实施计划。
- 修改代码、资源接线、构建脚本或 QA 脚本。
- 运行 `npm run build` 和提示词指定的 QA。
- 修改必要文档和新增开发复盘。
- 只暂存本轮相关代码和文档，提交到当前开发分支，并尝试推送到 Gitee。

## Kimi 默认不做什么

- 不擅自扩系统。
- 不重写 `RunEngine` 或主流程，除非提示词明确允许。
- 不用自己的判断覆盖当前设计基线。
- 不只改代码不改文档。
- 不把 `output/`、`progress.md` 或历史归档当成当前真相。

## 标准交接流程

1. 用户提出方向、问题或体验目标。
2. Codex 读取当前文档，判断下一轮优先级。
3. Codex 更新必要规则/设计/交接文档。
4. Codex 优先输出轻量任务卡；只有阶段切换或复杂任务才输出完整长提示词。
5. Kimi 按提示词开发、验证、提交。
6. 用户把 Kimi 回复给 Codex。
7. Codex 做验收判断，更新文档并决定下一轮方向。

## 轻量任务卡规则

- 默认优先使用 `doc/40_AI协作/Kimi任务卡模板.md`，只填写本轮变化项，减少重复上下文。
- 任务卡必须包含：一句话目标、最少必读文档、文件级导航、代码骨架草案、先验证后修复规则、验收命令、提交要求。
- 如果本轮只是补验、截图、QA 或小修，Codex 不再重复项目完整背景，只引用当前交接卡和最新复盘。
- 如果本轮涉及阶段切换、系统边界变化、玩法方向变化，才使用完整提示词。

## 文件级导航规则

- Codex 给 Kimi 的任务卡应尽量限定“本轮只需要看的文件”，避免 Kimi 每次读完整仓库。
- 文件级导航需要说明每个文件为什么要看，例如“`GameScene.ts`：Boss debug 入口接线”“`PilotAudio.ts`：cue ducking 层级”。
- 如果 Kimi 在执行中发现需要额外文件，必须在回复里说明原因。

## 先验证后修复规则

- 默认先跑验证，再决定是否改代码。
- 如果验证通过，只更新文档、截图索引或作品集材料，不强行改代码。
- 如果验证失败，只修失败项，不扩大成系统重构。
- Codex 给任务卡时应明确“通过时做什么”和“失败时允许修什么”。

## Gitee 提交规则

- 当前远端仓库为 Gitee：`origin = https://gitee.com/suwki/unity-learning.git`。
- Codex 每次完成文档、规则、设计、素材/音效方案或提示词沉淀后，必须执行一次 Git 提交，并在条件允许时推送到 Gitee。
- Kimi 每次完成代码开发、QA 脚本、资源接线或运行时修复后，必须执行一次 Git 提交，并在条件允许时推送到 Gitee。
- 提交前必须检查 `git status`，只暂存本轮相关文件，不混入历史脏文件、`output/`、临时文件或无关改动。
- 如果当前分支不是 `codex-dev`，必须先确认是否切换；不要直接把开发提交推到 `codex` 稳定基线。
- 如果 Gitee 推送失败，必须保留本地 commit，并在最终回复里明确说明失败原因和当前 commit hash。
- Codex 最终回复必须说明本轮提交号和推送状态；Kimi 最终回复也必须说明本轮提交号和推送状态。

## Kimi 提示词必须包含

- 明确要求“全程中文输出”。
- 本轮目标。
- 必读文档。
- 必读代码。
- 当前问题判断。
- 允许修改范围。
- 明确不允许做的事。
- 体验验收标准。
- 构建和 QA 要求。
- 文档同步要求。
- 最终回复格式。

## 当前推荐节奏

- Codex 轮：方向规划、文档整理、素材/音效预览、Kimi 提示词、Gitee 提交。
- Kimi 轮：代码开发、构建、QA、复盘、Gitee 提交。
- Codex 轮：验收 Kimi 结果、补文档、定下一轮。
