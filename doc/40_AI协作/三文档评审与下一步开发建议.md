# 三文档评审与下一步开发建议

## 适用范围

本文基于以下三份文档评审后得出：

- `doc/00_接手入口/当前交接卡.md`
- `doc/30_持续优化/开发复盘/2026-04-24_内容密度与分发权重小步补强.md`
- `doc/30_持续优化/开发复盘/2026-04-24_核心循环_关卡_战斗_成长补强.md`

本文的目标不是重复复盘内容，而是给下一位开发者一个更稳的判断：

- 这三份文档哪里已经合理
- 哪里还需要改写或补充
- 按当前 `/doc` 规则，下一轮最应该开发什么
- 下一轮不要做什么

---

## 总体判断

三份文档的方向整体是对的，而且彼此之间没有明显冲突。

当前项目主线已经比较清楚：

- 项目不再缺主流程
- 项目当前也不缺大系统
- 当前最重要的是把核心循环体验链继续收紧
- 当前剩余最明显短板已经逐渐聚焦到 `dash` 路线后段兑现、路线持续签名和局内即时读感

从开发顺序上看，`内容密度 / 分发权重` 和 `核心循环 / finalPrep / 第三轮收束` 这两轮数据补强已经把数据层缺口补到了一个合理阶段。下一轮不应该继续把主要精力放在 `contentSelectors / nodes / upgrades` 的抽法微调上，而应该优先把这些分发成果兑现到玩家真实能感受到的战斗体验上。

---

## 这三份文档里已经合理的地方

### 1. `当前交接卡.md`

合理点：

- 已经把当前阶段收口成“核心循环与核心战斗打磨轮”。
- 已经明确当前不该做地图扩写、Boss 大重构、UI 全主题重做和正式资产替换。
- 已经把后续风险收口到 `pierceFlow`、`dash`、精英 / Boss 样本稳定度几个点上。

这部分和 `START_HERE.md`、`doc/README.md`、`设计基线与约束.md` 的主口径是一致的。

### 2. `2026-04-24_内容密度与分发权重小步补强.md`

合理点：

- 目标聚焦，没有越界到重写系统。
- 对 `dash` 的判断是对的：问题不是完全没内容，而是中段不像路线。
- 处理手法是对的：优先补关键缺口和分发权重，而不是直接加大量模板。

这符合当前项目“先用数据补丁收紧体验，再决定是否扩内容”的基线。

### 3. `2026-04-24_核心循环_关卡_战斗_成长补强.md`

合理点：

- 对 `finalPrep` 的判断是对的，确实应该更像补拼图而不是最后一拍重开方向。
- 对第三轮职责的判断是对的，应该更偏收束，而不是继续并轨。
- 对 `dash` 的判断也对：当前短板已经不是前段 starter，而是后段 payoff 的兑现感。

这份文档已经具备直接指导数据层继续微调的价值。

## 文档还需要改进的地方

### 1. `当前交接卡.md` 还是略微偏长

虽然它已经比旧版干净很多，但现在第一个大段仍然保留了两轮同日补强的展开说明。  
按 `/doc` 的规则，这张卡更适合只保留：

- 当前阶段
- 当前一句话
- 当前主问题
- 最新落地结论
- 最新验证记录
- 当前风险
- 下一轮唯一主问题

建议把“内容密度与分发权重补强”和“核心循环_关卡_战斗_成长补强”两段收成各 1 到 2 句，并把细节继续留在对应复盘文档里。这样新接手者更容易在 1 屏内读完当前真相。

### 2. `2026-04-24_内容密度与分发权重小步补强.md` 的验证还不够强

这份复盘当前只有：

- `npm run build`
- 静态分布复核

按当前开发流程规则，这种“影响路线形成和关卡读感”的改动，最好至少再补一个轻量自然样本验证结论。哪怕不是完整自动化，也应该说明：

- 是否实际跑过自然样本
- `dash` 是否更稳定在 round 2 前后拿到战斗节点 + 承接牌 + 异常分叉
- 如果没跑，明确写“本轮只有静态验证，行为样本留到下一轮”

现在这份文档的风险是：它对静态结构解释得很清楚，但对真实游玩是否已经兑现讲得不够死。

### 3. `2026-04-24_核心循环_关卡_战斗_成长补强.md` 有一处表述建议更精确

文档里写“提高 `round-3-upgrade-commit-hold` 的 `dash` 路线加权”，这句话从“相对上一版”角度没有问题，但从当前数据观感上看，`dash` 仍不是这个节点里最强的路线倾向。

所以建议文案改成：

- “相对上一版提高 `dash` 的后段承接权重”
- “本轮目标是止住 `dash` 后段站稳感落后，不是让它在该节点变成最强倾向”

这样能避免后来的开发者误读成“这里已经足够支持 dash 了”。

## 按当前规则，下一轮最应该开发什么

如果严格遵守 `START_HERE.md` 里“每轮只解决一个主问题”的规则，下一轮最应该做的是：

## `dash` 路线后段 payoff 兑现专项

理由很简单：

- `内容密度与分发权重` 这一轮已经把 `dash` 的前中段结构补起来了。
- `核心循环 / finalPrep / 第三轮收束` 这一轮已经把后段分发边界收紧了。
- 当前交接卡和两篇复盘都反复指向同一个剩余短板：`dash` 的后段爽感、听感和持续签名仍弱于 `crit / pierce`。

也就是说，数据层已经给了 `dash` 更多“被抽到、被看见、被站稳”的机会，下一轮应该做的是让这些机会真正变成玩家能感到的收益，而不是再继续补抽法。

---

## 下一轮建议的开发范围

### A. 先补 `dash` 的后段 payoff 兑现

优先改这些文件：

- `src/data/upgrades.ts`
- `src/data/nodes.ts`

建议做法：

- 只挑 1 到 2 张 `dash` 后段 payoff / finisher 牌做高收益增强，不要再继续补 starter。
- 优先检查这些牌的实际兑现感是否足够：
  - `dash-return-hold`
  - `dash-afterimage`
  - `dash-anchor`
  - `dash-zero-window`
- 优先让后段 `dash` 更像“回线追回来以后能立刻占到便宜”，而不是继续只是更快、更能闪。

目标不是纯数值更高，而是让玩家在后段更明确感觉到：

- 我换位成功了
- 我借到了窗
- 我反打回来了
- 这一拍的 `dash build` 真的比前两轮更像成型路线

### B. 再补 `dash` 的局内持续签名

优先改这些文件：

- `src/scenes/GameScene.ts`
- `src/systems/PilotAudio.ts`

建议做法：

- 视觉上补“换位 -> 回切 -> 反打”短窗口签名，而不是再补长期常驻特效。
- 音频上沿现有 cue 和 route tint 做差异，不新开复杂音频系统。
- 明确让 `dash` 和 `pierce` 的听感分开：
  - `pierce` 是拉轨、穿层、清线回收
  - `dash` 应该是擦身、折返、借窗、追回主动权

这一步的核心不是加大效果，而是让 `dash` 在混战里有更稳定的“我刚刚完成了一次漂亮回摆”的即时反馈。

### C. 暂时不要再优先动 `contentSelectors.ts`

除非自然样本明确证明 `finalPrep` 仍频繁发散，否则下一轮不建议继续先动：

- `src/data/contentSelectors.ts`

原因不是它不能改，而是这两轮已经连续在补分发逻辑。现在更高价值的是验证这些逻辑有没有被战斗体验真正吃到。

---

## 下一轮不建议做什么

下一轮明确不建议：

- 不要继续补更多 `dash` starter
- 不要再开一轮大规模 `nodes / upgrades / anomaly` 扩容
- 不要把问题转成“再做一轮 finalPrep 抽法微调”
- 不要重写 `RunEngine`
- 不要为了做出 `dash` 爽感而堆满屏特效
- 不要一次性增加大量新 `AudioCue`

如果下一轮做成“又一轮分发表修补”，很容易出现文档看起来越来越完整，但玩家真实感受还是没真正追上的问题。

---

## 下一轮开发完成后的最低验收

按当前 `/doc` 规则，下一轮至少要补到这些验证：

1. `npm run build`
2. 一次自然 full-flow
3. 一次定向 `dash` 样本验证
4. 说明 `dash` 在后段是否更容易出现明确 payoff 时刻
5. 说明 `crit / pierce / dash` 的后段签名是否更容易分开
6. 新增一篇复盘，并更新 `当前交接卡.md`

如果只做了 build 和静态表复核，不够。

---

## 最终建议

如果你现在要直接排下一轮开发，我建议这样定题：

`下一轮主问题：dash 路线后段 payoff 兑现与持续签名补强`

这最符合三份文档共同指向的剩余问题，也最符合当前文档规则里“每轮只解决一个主问题”的要求。

如果这轮做完，后续再看：

- `finalPrep` 是否还会偶发过多泛用稳牌
- 精英裂口是否继续稳定读成“拆屏 -> 追本体”
- `屏卫主核` 的火线阶段是否仍稳

不要把这几件事和 `dash` 兑现轮混在一起做。
