# dash 兑现后下一步开发对接文档

## 文档目的

这份文档用于承接 `2026-04-24 dash 后段 payoff 兑现与持续签名补强` 之后的下一轮开发判断。

它回答的是：

- 这一轮 `dash` 专项之后，哪些问题已经不该继续硬补
- 当前还剩下的真正主问题是什么
- 下一轮开发应该如何收口，避免重新回到“继续堆内容”或“继续堆 dash 爽感”

---

## 当前结论

根据最新开发回报、当前交接卡和本轮复盘，现阶段判断如下：

- `dash` 已经从“结构上有”推进到“战斗里能感到”
- `crit / pierce / dash` 的后段签名比上一版更容易分开
- 这轮最重要的收益已经拿到：`dash` 不再只是能跑、能活，而是更容易出现“换位成功 -> 借到窗 -> 回切反打”的明确时刻

但这并不意味着下一轮应该继续直接给 `dash` 加更多兑现。

当前最大风险已经从“`dash` 太弱”切换成：

- `dash` 的后段兑现是否只在定向样本里明显，而在自然 full-flow 里不够稳定
- `dash` 的补强是否会慢慢把普通战回报链、精英裂口读感和 Boss 收尾带偏

所以，下一轮最应该做的不是继续做 `dash` 强化轮，而是做一轮：

## 自然样本稳定性与关键监控项收口

---

## 为什么下一轮不该继续直接补 dash

原因不是 `dash` 已经完美，而是当前阶段更需要先确认它没有越界。

### 1. 定向样本已经证明“能成立”

这一轮开发已经拿到了定向 `dash` 样本：

- `dashPicks = 4`
- `routeFocusSeen = ['dash']`
- `lateDashWindowMoments = 8`
- `dashCounterMoments = 3`

这说明 `dash` 兑现窗口已经能做出来。  
下一轮继续同方向硬加，很容易把原本“刚好成立”的窗口推成“只剩 dash 最有戏”。

### 2. 当前最重要的是看“自然流里稳不稳”

当前还没被彻底说明白的是：

- 普通样本里 `dash` 后段高光是不是也能自然出现
- 这些高光是不是会牺牲普通战清线读感
- 精英裂口和 Boss 火线阶段是否仍然保持原本的解题结构

### 3. 当前项目的阶段约束不支持继续横向膨胀

根据 `设计基线与约束.md` 和 `当前交接卡.md`：

- 当前不是地图扩写轮
- 当前不是 Boss 大重构轮
- 当前不是路线内容池扩容轮
- 当前也不是正式资产替换轮

下一轮继续给 `dash` 扩牌、扩节点、扩 cue，很容易又脱离当前阶段判断。

---

## 下一轮唯一主问题

如果严格遵守“每轮只解决一个主问题”，下一轮建议定题为：

## `dash` 补强后的自然样本稳定性与 Boss / 精英监控收口

这轮的核心不是再做新爽点，而是回答三个问题：

1. `dash` 的后段 payoff 是否能在自然 full-flow 里稳定成立
2. 精英裂口是否仍稳定读成“拆屏 / 裂口 / 追本体”
3. `屏卫主核` 的火线阶段是否仍然够厚、够稳，没有被局部手感优化带薄

---

## 下一轮建议开发范围

### A. 先补观测，而不是先补内容

优先查看并按需修改：

- `src/systems/RunEngine.ts`
- `src/systems/MetricsTracker.ts`
- `src/scenes/GameScene.ts`
- 如有必要，查看现有 `output/playwright/` 下相关验证脚本

建议做法：

- 给 `dash`、精英裂口、Boss 火线阶段补最小必要的运行时观测点
- 让后续自然样本验证不只靠主观感受，而能回收一些最小统计

优先关注这些指标：

- `lateDashWindowMoments`
- `dashCounterMoments`
- `eliteCrackSeen`
- `eliteCrackFollowThroughMoments`
- `bossFirelineCoverage`
- `bossSafeWindowMoments`
- 普通战中 `kill -> pickup -> continue firing` 的连续样本

注意：

- 这里只允许补最少量高收益观测
- 不要把这一轮做成复杂埋点系统升级

### B. 只在自然样本证明有问题时，做最小必要数值 / 模板修正

优先可能涉及：

- `src/data/balance.ts`
- `src/data/battleTemplates.ts`
- `src/data/nodes.ts`

建议做法：

- 如果自然样本显示 `dash` 后段在普通流里仍偶发过弱，再做最小必要修正
- 如果自然样本显示 `dash` 高光把普通战读局或 Boss 收尾带偏，就优先收一点，而不是继续加

这轮的数据层原则是：

- 只做证据驱动修正
- 不做预设式继续强化

### C. 对音频与表现的工作重心从“新增”切成“防回退”

优先查看并按需修改：

- `src/scenes/GameScene.ts`
- `src/systems/PilotAudio.ts`

建议做法：

- 优先确认 `dash` 新签名在自然样本里确实可见 / 可听
- 同时确认它没有盖掉：
  - `hurt`
  - `nearMiss`
  - `pressure`
  - `enemyShot`
- 确认它没有让 `pierce` 的长轨清线和 `crit` 的收束爆发变得更难区分

这轮不追求更花，而是追求不回退。

---

## 下一轮不建议做什么

下一轮明确不建议：

- 不要继续补 `dash starter`
- 不要继续补更多 `dash payoff` 或 `dash finisher`
- 不要继续扩 `nodes / upgrades / anomaly` 内容池
- 不要把问题重新改写成 `finalPrep` 抽法专项
- 不要开新的路线专项视觉大包装
- 不要新增大量 `AudioCue`
- 不要把验证轮做成“纯写脚本不改游戏”或“纯改游戏不补验证”

---

## 下一轮最低验收

按当前文档规则，下一轮至少要完成：

1. `npm run build`
2. 一次自然 full-flow 验证
3. 至少一轮更长的自然样本复检
4. 一次定向精英裂口样本
5. 一次定向 Boss 火线样本
6. 明确说明：
   - `dash` 后段 payoff 是否在自然流里稳定成立
   - 精英裂口是否仍稳定读成“拆屏 -> 追本体”
   - `屏卫主核` 火线阶段是否仍稳
   - 普通战回报链是否没有被带偏

如果这轮只做 build，不够。  
如果这轮只做定向样本，不够。  
如果这轮只做自然样本但没有对应监控说明，也不够。

---

## 当前推荐的下一轮开发标题

建议下一轮直接定题为：

`自然样本稳定性与Boss/精英监控收口`

这比继续叫“dash 补强”更符合当前项目真相。

---

## 最终建议

`dash` 这一轮已经够了，至少够进入“验证它是不是真的成立”的阶段了。

下一轮最成熟的做法不是继续给它加，而是：

- 用自然样本确认它稳不稳
- 用精英 / Boss 定向样本确认它有没有带偏关键监控项
- 只在证据明确时做最小必要修正

也就是说，下一轮的正确姿势是：

`先看它会不会歪，再决定要不要继续推。`
