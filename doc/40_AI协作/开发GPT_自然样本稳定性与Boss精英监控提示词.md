## 三、本轮任务

本轮唯一主问题是：

`dash 补强后的自然样本稳定性与 Boss / 精英监控收口`

这轮的核心不是继续制造新高光，而是确认当前已经补上的 `dash` 后段兑现：

- 是否能在自然 full-flow 里稳定成立
- 是否会把普通战回报链带偏
- 是否会影响精英裂口的“拆屏 -> 追本体”读感
- 是否会把 `屏卫主核` 的火线阶段做薄

你这轮必须至少覆盖以下三件事中的核心部分：

### A. 补最小必要的观测与调试出口

优先查看并按需修改：

1. `src/systems/RunEngine.ts`
2. `src/systems/MetricsTracker.ts`
3. `src/scenes/GameScene.ts`
4. 如有必要，相关验证脚本

要求：

- 只补最少量高收益观测，不开复杂新系统
- 优先让这些状态更容易被验证或导出：
  - `lateDashWindowMoments`
  - `dashCounterMoments`
  - `eliteCrackSeen`
  - `eliteCrackFollowThroughMoments`
  - `bossFirelineCoverage`
  - `bossSafeWindowMoments`
  - 普通战中 `kill -> pickup -> continue firing` 的连续样本

### B. 在样本证明有偏移时，做最小必要修正

优先可能涉及：

1. `src/data/balance.ts`
2. `src/data/battleTemplates.ts`
3. `src/data/nodes.ts`
4. 如有必要，再看 `src/systems/PilotAudio.ts`

要求：

- 只允许做证据驱动修正
- 如果自然样本显示 `dash` 后段不稳，可以小修
- 如果自然样本显示 `dash` 高光盖掉普通战读局、精英裂口或 Boss 收尾，也必须优先收回一点
- 不允许预设式继续增强 `dash`

### C. 防回退检查

你必须确认本轮没有把这些东西带坏：

1. 普通战“击杀 -> 掉落 -> 吸附 / 拾取 -> 继续开火”回报链
2. 精英裂口的“拆屏 -> 裂口 -> 追本体”读感
3. `屏卫主核` 的火线阶段覆盖率和压迫感
4. `hurt / nearMiss / pressure / enemyShot` 的危险语义层级
5. `crit / pierce / dash` 三路线的后段差异

## 四、本轮允许做的事

本轮允许优先处理：

- 补最少量运行时观测
- 补最少量 debug / metrics 导出
- 调整少量参数以修正自然样本下的偏移
- 调整精英裂口或 Boss 火线阶段的最小必要参数
- 调整极少量 `dash` 相关表现或音频，使其不压制危险层
- 强化验证脚本和验证说明

## 五、本轮不允许做的事

本轮禁止：

- 重写 `RunEngine`
- 继续做 `dash` 爽感强化轮
- 继续扩 `dash starter / payoff / finisher`
- 再开一轮大规模 `nodes / upgrades / anomaly` 扩容
- 把问题重新转成 `finalPrep` 抽法专项
- 开新的音频系统
- 新增大量 `AudioCue`
- 做大规模视觉重包装
- 只改代码不补验证
- 只补验证不回看游戏是否需要最小修正

## 七、Git 与分支规则（硬约束）

本项目默认开发分支为：`codex-dev`

固定规则：

1. 每次开始前先执行 `git branch --show-current`
2. 如果当前不在 `codex-dev`，先切到 `codex-dev`
3. 每次修改完代码或文档后，必须提交到 `codex-dev`
4. 每轮结束后至少执行：
   - `git status`
   - `git add <本轮相关文件>`
   - `git commit -m "自然样本稳定性与Boss精英监控收口"`
   - `git push origin codex-dev`

额外分支纪律：

- `codex` 分支永远要比 `codex-dev` 少一次 commit
- 不要把当前最新一轮开发直接推到 `codex`
- 不要让 `codex` 和 `codex-dev` 指向同一个最新提交
- `codex` 视为“上一轮稳定基线”，`codex-dev` 视为“当前开发前沿”
- 除非用户明确要求，否则不要主动把 `codex` 追平到 `codex-dev`

如果 push 失败，必须在输出中明确说明。
