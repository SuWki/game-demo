## 项目当前真相

### 一句话产品

这是一个基于 `Phaser + TypeScript + Vite` 的短局节点推进自动射击原型。  
玩家体验重点不是大地图探索，而是：

- 快速开局
- 在短局战斗中成型三条路线之一
- 在精英与 Boss 压力下读局、走位、追回节奏
- 用一个短而有收束力的结果页完成本局体验

### 当前已经存在的页面

- 开始页
- 战斗 HUD
- 节点选择页
- 强化选择页
- 异常事件页
- 最终整备页
- 结果页

### 当前明确不存在的页面

- 设置页
- 商店页
- 图鉴页
- 背包页
- 常驻装备栏
- 常驻技能树
- 长剧情对话页
- 大型统计报表页

开发不得擅自为了“更完整”扩出这些页面。

### 当前主实现模块

- `src/scenes/MainMenuScene.ts`
- `src/scenes/GameScene.ts`
- `src/scenes/ResultScene.ts`
- `src/ui/OverlayController.ts`
- `src/systems/RunEngine.ts`
- `src/systems/PilotAudio.ts`
- `src/systems/MetricsTracker.ts`
- `src/game/types.ts`

这条链路已经覆盖：

- 主流程页面切换
- 战斗状态推进
- HUD 与选择面板同步
- 结果页收口
- 音乐状态切换与关键 cue
- 调试面板与基础验证

当前开发优化应该围绕这条链路增量增强，不应该把它整条推翻重来。

## UI / 美术 / 音频对开发的硬约束

### UI 侧硬约束

- UI 是战斗系统的外延，不是后台工具面板，也不是平台落地页。
- 所有页面必须优先保护中场可读性，尤其是 `960x540` 视口下的战斗核心区。
- 结果页不能是空页，但也不能做成报表堆砌；它的职责是完成情绪收束、路线回顾和重开推动。
- 节点页、强化页、异常页、整备页必须延续同一套信息架构，不要每个面板都像不同产品。

### 美术侧硬约束

- 当前美术方向是“冷核机体 vs 热态火线”，而不是写实角色驱动项目。
- 玩家、普通敌人、精英、Boss、XP 球、敌方投射物、危险区、安全窗必须保持稳定的识别色与轮廓差异。
- 大量战斗语义对象仍应保持程序化绘制，例如危险区、裂口、压制带、安全窗、火线走向提示。
- 当前不适合优先投入大插画、重背景、长剧情立绘、大体量骨骼动画。

### 音频侧硬约束

- 当前音频目标是“读局反馈优先”，不是“先做完整音频内容管线”。
- 音乐状态仍以 `menu / battle / boss / result` 四态为主。
- 关键 cue 仍以当前 `AudioCue` 为稳定语义边界，不要一次性扩出大批新枚举。
- 可以做轻量 cue profile、变体、route tint、encounter tint、intensity tint，但不要先上重型中间件或复杂资源系统。

## 现在最该开发的东西

### 1. 统一实现层 token 与 helper

优先把视觉和音频的“重复逻辑”从散落状态收紧，而不是先追求资产量。

应该做：

- 提炼战斗对象颜色、描边、发光、层级的统一 token
- 抽离 HUD / 面板 / 页面锚点共用样式和排版常量
- 把 `GameScene.ts` 中重复的绘制语义整理成更稳定的 helper
- 把 `PilotAudio.ts` 中 cue profile、上下文 tint、轻量变体策略收成可维护结构

不应该做：

- 直接把现有程序化对象全部资源化
- 为了“方便接素材”先重写一整套渲染或音频系统

### 2. 补足三路线中的场内差异，尤其是 `pierce`

当前文档对三路线表达已经更完整，但实现侧的稳定可见差异仍然偏向 `crit` 和 `dash`。  
开发应把 `pierce` 的场内存在感补起来，优先做“持续签名”而不是只做瞬时亮点。

应该补：

- `pierce` 的弹道延续感、穿透后的残留语义或轨迹收束
- 与 `crit` 爆点、`dash` 位移脉冲明确不同的视觉节奏
- 与之对应的轻量音频差异，而不是单独堆一组巨大新 cue

### 3. 把美术规格转成“可替换边界”，而不是直接压开发接素材

`美术资产规格表.md` 现在已经够具体，开发要做的是：

- 判断哪些对象继续程序化最划算
- 判断哪些对象值得做成“可替换资源入口”
- 给未来美术接入预留干净边界

现阶段优先适合做可替换入口的对象：

- 玩家主体轮廓或核心图形
- 四类普通敌人的轮廓贴图或图标化外形
- 精英核心与护卫标记
- Boss 关键阶段锚点图形
- 页面锚点、按钮底板、标签条、结果页重点徽记

现阶段更适合继续程序化的对象：

- 安全窗
- 危险遮罩
- 压力带
- 裂口楔形
- 大多数战斗底纹和瞬时警示

### 4. 把音频文档转成“轻量接线升级”，不是正式音频工程

根据当前文档和代码，音频开发要做的是：

- 巩固现有 `AudioCue` 间的可分辨性
- 利用 `setCombatContext(...)` 的 `routeFocus / encounter / intensity` 做轻量上下文差异
- 为未来资源替换预留最小可行接口

当前接线事实：

- `MainMenuScene.ts` 负责菜单音乐
- `GameScene.ts` 负责战斗态、Boss 态、结果态切换，以及战斗上下文同步
- `ResultScene.ts` 负责结果页音乐
- `PilotAudio.ts` 负责音乐、SFX、ducking、snapshot 与 cue 执行

开发不要误判成“文档写了资产清单，所以现在要立刻做完整导入系统”。

## 推荐开发顺序

1. 先做视觉和音频 token / helper 收口
2. 再补 `pierce` 的视觉与听感持续签名
3. 再优化开始页、HUD、结果页的锚点一致性和信息密度
4. 再为美术资源和音频资源各补一层最小可替换接口
5. 最后才考虑少量高收益的新事件触发点

## 模块级对接说明

### `src/scenes/MainMenuScene.ts`

负责开始页进入体验的第一印象。  
开发重点：

- 开始页按钮层级是否清晰
- 视觉锚点是否能快速说明“这是战斗原型，不是工具页”
- 菜单音乐是否足够和战斗态区分

### `src/scenes/GameScene.ts`

这是当前 UI / 美术 / 音频需求的主落点。  
开发重点：

- 玩家、敌人、投射物、危险区、安全窗、精英裂口、Boss 火线的识别关系
- HUD 与节点 / 强化 / 异常 / 整备面板的切换节奏
- `syncAudioState(...)` 对上下文的传递是否稳定
- 三路线差异是否在实战中被持续读到

### `src/scenes/ResultScene.ts`

负责局后收束。  
开发重点：

- 结果页是否足够“有内容但不拥挤”
- 是否展示对玩家最有意义的收口信息
- 是否保留强烈的重开意愿

### `src/ui/OverlayController.ts`

负责页面、HUD、面板和 toast 的前端承接。  
开发重点：

- 主次按钮、标签条、标题层级、摘要信息是否统一
- 节点页 / 强化页 / 异常页 / 整备页是否共享一套布局规则
- 结果页是否还有空心感

### `src/systems/PilotAudio.ts`

负责当前音频骨架。  
开发重点：

- 现有 cue 的可辨识度
- route tint / encounter tint / intensity tint 的轻量落地
- 资源替换接口是否足够轻、不破坏现有结构

### `src/systems/RunEngine.ts`

负责战斗、节点、成长与结果主循环。  
开发重点不是重写系统，而是确认：

- 有没有值得为 UI / 美术 / 音频新增的最小事件出口
- 新出口是否真的高收益
- 是否会破坏现有主循环稳定性

### `src/game/types.ts`

负责共享语义边界。  
开发重点：

- `AudioCue` 不要膨胀失控
- 共享 UI / HUD / 页面语义尽量通过稳定类型表达
- 新增字段必须服务当前真实读局问题，而不是为了预留而预留

## 开发不该做的事

- 不要把文档里“未来正式化素材方案”直接当成这一轮必须一次做完的工程目标
- 不要新增与当前玩法无关的大页面
- 不要为了美术接入而重写当前战斗渲染主链
- 不要为了音频接入而引入重型 middleware
- 不要让结果页重新变成空页面或纯报表页面
- 不要让 HUD 和面板侵占中场，破坏战斗读局

## 验收方式

开发交付时至少完成以下验证：

1. `npm run build`
2. 开始页 -> 战斗 -> 节点 / 强化 / 异常 / 整备 -> Boss / 结果页 的完整流程走查
3. `crit / pierce / dash` 三路线主观差异复核
4. 玩家 / 普通敌人 / 精英 / Boss / 敌方投射物 / XP 球 的识别复核
5. 结果页是否空、是否乱、是否能推动重开
6. `shoot / hit / kill / pickup / hurt / nearMiss / enemyShot / pressure` 的可分辨性复核
7. 菜单 / 战斗 / Boss / 结果 四态音乐切换复核
